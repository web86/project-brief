# Project Brief v0.9.6 — Jino deployment and rollback

This is an instruction for a separately authorized deployment. Preparing this release does not authorize push, deployment, production DB changes or real provider connections. PHP 8.4, required extensions, private/public separation, existing cron and hosting preflight remain as documented in DEPLOY-JINO.md. Local QA does not verify Jino/FPM, production load, TLS settings, backups or physical MFA devices.

## Update from v0.9.5

1. Verify ZIP SHA-256 and CRC. Keep the verified v0.9.5 runtime plus a coordinated pre-update DB/storage backup, .env and APP_KEY; test restore on staging. Run staging with distinct keys/sessions and external delivery disabled. Never copy QA fixtures or test secrets into production.
2. Enter maintenance: `php artisan down`. Let current requests finish. Replace the matching private/public runtime with v0.9.6, preserving `.env`, APP_KEY, storage and permissions. Never use migrate:fresh in production.
3. Run `php artisan migrate --force --no-interaction`, then `php artisan optimize:clear` and the existing production cache commands. Migration `2026_10_30_213603_add_external_agents` is additive: external identity/grants, nullable agent participant/credential/webhook/comment references, assignment/report/operation tables. Existing human participants, tokens, SSO, comments and task workflow are preserved. No agent or permission is granted automatically. No provider keys or billing settings are introduced.
4. Preserve the existing bounded `integrations:webhooks` cron. No new scheduler/daemon or persistent polling is required. Each cron run retains existing 20-delivery/45-second defaults (bounded by six retries and 8-second requests). Review actual Jino capacity and cron overlap on staging before enabling real agents. Existing processing lease prevents overlapping runners. Agent API uses existing IP/workspace and separate credential rate limiting.
5. While still in controlled staging, create an agent as owner, explicitly authorize only a test project, issue minimal scopes and optionally configure a public HTTPS webhook. Add the agent to Team and assign a task. Run the independent demo externally. Check its agent-authored comment/report/file, human review and unchanged client approval/task status. Check assigned-project superadministrator versus ordinary administrator/client/second workspace.
6. Revoke assignment, project membership, owner grant, credential and registration in turn. Check 404/401 after each boundary and suppression of pending webhook deliveries. Rotate credentials and signing secrets; previously issued values must fail. Check audit contains agent/credential identifiers and safe metadata only, with no raw token or body.
7. Verify RU/EN/TR/ZH-CN, light/dark/system, 1440/390 px, modal keyboard/Escape, one-time secret, team identity, result links and file downloads. Verify original REST API/SSO/webhooks/private chat regression gates. Ensure private uploads remain outside document root. Check PHP upload limits cover documented file sizes, HTTPS, secure cookies, operational logs and existing notification delivery.
8. Enable with `php artisan up` only after the separately approved deployment smoke checks. Refresh old browser/PWA tabs. Store credentials only in the external executor's secret manager and never in URLs or production task descriptions.

## Rollback

The migration intentionally refuses `down`: agent results, authorship and credential binding must not be silently erased or reinterpreted by older runtime. Do not launch v0.9.5 against the v0.9.6 schema without a reviewed compatibility fix. Do not run migrate:rollback, drop agent fields, clear histories or repurpose agents as human users.

Preferred recovery is a compatible forward fix: maintenance, disable external executors/revoke credentials, back up current DB/storage, test corrected runtime on a copy, replace matching private/public assets, clear caches and verify isolation before up.

A full downgrade requires a separately approved coordinated v0.9.5 runtime + pre-v0.9.6 DB + matching private storage + original APP_KEY. Preserve the current DB/storage separately for controlled recovery of subsequent work. This loses post-backup changes in the active database and requires the owner's explicit approval. Ensure old credentials/deliveries cannot remain active, restore the pair while in maintenance, verify existing private chat and MFA/SSO, then up. Older pre-v0.9.5 runtime has additional private-channel exposure risks; follow its recorded rollback restrictions.
