## Архитектура и права

Модели User, WorkspaceMember, ProjectMember и роли owner/admin сохранены. `ProjectPermissions` вычисляет права только по authenticated User, активному членству в выбранном workspace и назначению на конкретный проект. Владелец имеет все права в своём workspace. Контекст кешируется исключительно внутри одного HTTP-запроса; новые запросы читают актуальные назначения и полномочия. Список проектов сохраняет постоянное число запросов независимо от их количества.

| Разрешение                     | По умолчанию | Защищённые операции                                        |
| ------------------------------ | ------------ | ---------------------------------------------------------- |
| `manage_structure`             | Да           | Создание, изменение, сортировка, удаление разделов         |
| `manage_clients`               | Нет          | Список/данные клиентов, изменение, создание и отзыв ссылок |
| `manage_project_settings`      | Нет          | Обновление названия, сайта, валюты, статуса проекта        |
| `manage_project_notifications` | Нет          | Чтение/изменение правил, получателей, тестовая отправка    |
| `export_project`               | Нет          | Генерация PDF/DOCX, включая внутренние поля в документе    |
| `manage_trash`                 | Нет          | Список корзины и восстановление идей                       |

JSON `project_members.permissions` допускает только эти шесть ключей и JSON boolean. Неизвестные ключи, строки/числа вместо boolean, права для неназначенных/чужих проектов отклоняются. `null` у прежних и новых назначений означает безопасные значения по умолчанию. Повторное приглашение не сбрасывает ранее выданные права. Изменять назначения и права может только владелец; роль владельца через эту форму не передаётся.

Разрешения не заменяют ProjectAccess. Чужой UUID и отозванное назначение дают 404, отсутствие отдельного полномочия — 403 с `project_permission_denied`. Восстановление по UUID идеи сначала проверяет TaskAccess, затем полномочие её проекта. Клиентские magic-link и экспорт клиента продолжают использовать прежний отдельный контур доступа.

Обычные идеи, статусы, оценки/технические заметки в рабочем интерфейсе разработчика, комментарии, вложения, перемещение идей между существующими разделами и персональные уведомления не зависят от административных переключателей. Чтение разделов доступно для этих операций. Создание произвольного раздела через форму идеи также проверяет `manage_structure`; сравнение названий совпадает с ProjectStructure, включая регистр при нечувствительной collation MariaDB. Для пустого проекта допускается системный раздел «Общее», чтобы запрет управления структурой не блокировал первую идею. Удаление новой несогласованной идеи остаётся обычной операцией; просмотр корзины и восстановление требуют отдельного права.

## Дополнительное требование: создание проектов

По уточнению пользователя вместо безусловного запрета для всех разработчиков добавлено отдельное `workspace_members.can_create_projects`, по умолчанию false. Владелец меняет его в редакторе участника, вне настроек выбранного проекта. Оно действует только в этом workspace, в том числе для участника без назначенных проектов. Владелец сохраняет право создавать проекты автоматически.

Созданный разработчиком проект автоматически назначается ему с шестью безопасными проектными правами по умолчанию. Другие проекты и workspace не открываются. Создание workspace, управление командой и owner-роль не делегируются. Исключение из команды сбрасывает разрешение создания: повторное приглашение исключённого участника не восстанавливает прежний grant. Повторное приглашение активного участника сохраняет действующие права. Отзыв разрешения блокирует следующий POST, включая отправку ранее открытой формы; уже созданные проекты и назначения сохраняются. `/api/admin/me` и личные уведомления возвращают эффективное `canCreateProjects`; перед открытием формы создания frontend обновляет его с сервера.

## Интерфейс

«Команда» → «Проекты и права»: назначения проектов, отдельный переключатель создания проектов в workspace, явный выбор проекта для шести полномочий, пояснения, сохранение, сброс только выбранного проекта. Права разных проектов не объединяются.

`projectMenu` содержит соответствие разделов разрешениям; общий helper используется маршрутизацией и ProjectNavigation для desktop/mobile. Сохранены AppIcon, текущие размеры/сетка, активный фон и цвет, счётчики, разделитель корзины, light/dark и RU/EN. Карточки проектов и кнопки сортировки разделов также учитывают права. `/admin/projects/:uuid` открывает идеи; старый `#client-access` проходит проверку разрешения. Закрытая страница объясняет ограничение и предлагает вернуться к идеям. При переходах в административные разделы запрашивается свежий summary проекта. Уже полученные данные открытой страницы не удаляются из памяти по таймеру, но любая следующая защищённая операция проверяется сервером и после отзыва отклоняется. Защита несохранённых рабочих черновиков сохранена.

## Проверки

- Полный Laravel-набор: **587/587** на SQLite (5939 assertions) и **587/587** на MariaDB 11.8 (5944 assertions), включая приглашения, аккаунт, multi-tenant изоляцию, уведомления, экспорты и прежние миграции.
- Новые feature-тесты: все защищённые endpoints; индивидуальное включение/отзыв каждого права; разные права в двух проектах; отзыв назначения и workspace switch; whitelist/boolean/owner защита; сохранность комментариев/вложений/событий; идеи в пустом проекте; выдача/отзыв создания проектов, его независимость от workspace и отсутствие самоповышения.
- Upgrade-тест на SQLite/MariaDB: существующие пользователи, workspace, проекты и назначения побайтово сохраняются, новые поля получают безопасные значения; rollback/reapply проверены дважды. Прежние legacy migration tests также запускаются на отдельной MariaDB.
- Frontend: 221 тест, включая меню для каждого права в обоих языках и ориентациях, прямые URL, обновление прав, отзыв создания при кешированной навигации, черновики и прежние регрессии.
- Реальный Laravel browser E2E: 16 сценариев/конфигураций, database sessions, CSRF, временная SQLite и локальный SMTP-приёмник (6 писем), без JS-ошибок. Каждое право отдельно; прямые URL/API; отзыв при открытых настройках; разные права двух проектов; создание своего проекта и отзыв при открытой форме; обычная идея без административных прав; профиль, подтверждение Email, смена/восстановление пароля. Восемь вариантов формы прав: 1440/390px × RU/EN × light/dark, независимое сохранение/сброс.
- Регрессионные browser E2E: навигация — 10; персональные уведомления/клиентская навигация — 35; операции идей/корзина — 20; Milestone 4.6 quick — дополнительные сценарии проектных и личных уведомлений.
- Production build, Pint, Prettier, `git diff --check`; сборщик проверяет no-dev vendor/assets, исключение secrets, runtime упакованного приложения и целостность ZIP.

Точные результаты автоматических проверок сохранены в [QA.json](QA.json), интеграционные сценарии — в [browser-results.json](browser-results.json). Мобильные проверки выполнены в Chromium с эмуляцией touch/390px. Физический телефон, Safari и SMTP Jino в этой задаче не использовались; живую доставку пользователь проверяет самостоятельно по прежней договорённости.
