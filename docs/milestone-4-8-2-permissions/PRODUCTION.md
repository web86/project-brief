# Milestone 4.8.2 — production deployment и откат

Поставка — полный ZIP: `private/project-brief-app/` с production vendor, `public/` с готовыми frontend assets, инструкции и `release.json` с SHA исходников. Предыдущие Milestone и UI polish `0ac5cd3` включены. Доставка на Jino, push и GitHub Release не выполнялись.

## Перед обновлением

Сделайте согласованную резервную копию БД, private code/vendor, public assets, действующих `.env`, APP_KEY и всего `storage/` (uploads/avatars). Сохраните настройки SMTP/Telegram/Push и версию прежней поставки. Проверяйте checksum ZIP до распаковки. ZIP и каталог private должны находиться вне document root.

Требования прежние: PHP 8.3+ (целевой production 8.4), расширения из DEPLOY-JINO.md, Argon2id, GD JPEG/PNG/WebP, writable `storage/` и `bootstrap/cache/`. Новых зависимостей и параметров `.env` нет. Не меняйте APP_KEY и секреты интеграций. Не переносите тестовые параметры Argon из автоматических тестов.

## Установка поверх существующего приложения

1. В действующем `~/project-brief-app/`: `php artisan down`.
2. Загрузите `private/project-brief-app/` из ZIP в `~/project-brief-app/`, `public/` — в `~/domains/brief.web86.site/` по текущей схеме Jino. Vendor замените целиком. Сохраните действующие `.env`, всё `storage/`, включая maintenance marker. Удалите устаревшие compiled cache files из `bootstrap/cache`, сохранив сам каталог.
3. В каталоге приложения выполните:

```sh
php artisan config:clear
php bin/check-server
php artisan migrate --force
php artisan optimize
php artisan up
```

Не выполняйте `key:generate`, `migrate:fresh`, `db:wipe`, seed или first-install на рабочей установке. Node/npm/Composer на Jino не требуются.

Новая additive миграция `2026_10_25_180202_add_permissions_to_project_members_table` добавляет:

- `project_members.permissions`: nullable JSON. Существующий NULL трактуется как structure=true, остальные пять прав=false.
- `workspace_members.can_create_projects`: boolean, default false. Owner получает эффективное разрешение независимо от этого значения.

Таблицы, memberships, назначения, пользователи и история не пересоздаются. Заполнения/сброса прежних проектных данных нет. `migrate --force` повторно ничего не меняет. Неприменённые прежние миграции выполнятся штатно; для обновления с версий до 4.8 дополнительно прочитайте прежнюю инструкцию по приглашениям/аккаунту и совместимости Argon2id.

После обновления прежние non-owner теряют административные права, кроме структуры, а создание проектов выключено. Это ожидаемый безопасный default. Владелец выдаёт нужные полномочия через «Команда» → «Проекты и права». Сохранённые назначения остаются доступны для обычной работы с идеями.

## Ручная приёмка после установки

- Health, прежний вход владельца, проекты, клиентский magic-link, создание/обсуждение идеи, PDF/DOCX владельца.
- Разработчик с базовыми правами видит идеи/обсуждения/структуру; клиенты, настройки, уведомления проекта, экспорт и корзина закрыты, включая прямой URL и API.
- В команде выберите конкретного разработчика и проект, включите каждое право отдельно, сохраните; в другой сессии проверьте соответствующий раздел. Выдайте разные права двум проектам и проверьте независимость; сброс меняет только выбранный проект.
- Отзовите право настроек при открытой форме разработчика: следующий PATCH получает 403, данные не меняются. Уберите назначение проекта: следующий API получает 404, список исключает проект, другие назначения сохранены.
- Отдельно включите «Разрешить создание проектов»: разработчик создаёт проект в текущем workspace, видит его с базовыми правами; управление командой недоступно. Отзовите разрешение при открытой форме: следующий POST получает 403. Созданный ранее проект сохраняется. Другое workspace не наследует разрешение.
- Проверьте собственный аккаунт, личные уведомления, Telegram/Push, desktop/mobile, RU/EN и light/dark. Клиент не видит административных полномочий.

Новой SMTP-конфигурации нет. Реальную доставку Jino пользователь проверяет вручную по прежней договорённости; автоматические интеграционные тесты использовали локальный SMTP-приёмник.

## Откат

Предпочтительно исправление вперёд. Для полного отката: maintenance → сохранить текущую БД/uploads для разбора → восстановить согласованный backup БД, private code/vendor, public assets и storage → сохранить соответствующий APP_KEY → очистить/пересобрать cache → проверить owner/client доступ → up. Данные после backup нужно переносить отдельно, иначе они потеряются.

Откат только к прежнему коду восстанавливает его более широкие non-owner права, поскольку прежний backend не проверяет новые разрешения. До такого отката ограничьте доступ разработчиков и проверьте правила доступа; простое возвращение старого UI не сохраняет введённые ограничения.

На production не запускайте общий `migrate:rollback`: он может откатить весь batch и прежние миграции. Новые additive поля можно оставить при временном возврате к прежнему совместимому коду. `down()` удаляет только эти два поля и уничтожает выданные полномочия; он предназначен для контролируемого тестового rollback/reapply, а не замены резервной копии. Совместимость паролей Argon2id из 4.8 должна сохраняться при любом откате.
