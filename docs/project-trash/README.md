# Все проекты: карточки и корзина

Реализация от 26 октября 2026 года, release 0.6.3. Состояние сборки и публикации фиксируется отдельно в `RELEASE-ARTIFACT.json`. Production deployment не выполняется.

## Поведение

- Карточка показывает название со ссылкой, активность, `projects.updated_at`, сайт, число прикреплённых клиентов, число назначенных активных разработчиков (роль `admin`, без владельца), код существующей валюты и прогресс. Процент округляется до целого; пустой проект — 0%. Завершёнными считаются задачи со статусом `done`, задачи с `deleted_at` исключены. Агрегаты получаются через SQL `withCount`, без загрузки коллекций клиентов/задач на каждую карточку. Дата обновления относится к записи проекта, а не к последнему изменению задачи.
- «Открыть» и название ведут в brief. «Клиенты», «Команда» и «Настройки» ведут к выбранному UUID. Действуют прежние права: команда доступна владельцу, клиенты/настройки — по разрешениям проекта.
- Красная иконка `trash-2` находится последней. Перемещение требует диалога подтверждения и действующего `manage_trash`. То же право требуется для просмотра своей доступной корзины и восстановления. У клиента этих возможностей нет.
- При перемещении исходный `status` сохраняется в `status_before_trash`, статус становится `inactive`, устанавливается `deleted_at`. Сам по себе `inactive` не означает удаление.
- Корзина по умолчанию закрыта. В ней показаны только доступные пользователю удалённые проекты текущего workspace. Счётчик у разработчика относится к проектам, где ему дано `manage_trash`.
- Восстановление очищает `deleted_at`, возвращает исходный статус и сохраняет задачи (включая собственную корзину задач), комментарии, файлы, настройки, токены доступа и назначения участников. Клиентский доступ к изначально неактивному проекту остаётся неактивным. Отдельно отозванные ссылки и права не активируются.
- Удаление навсегда и очистка доступны только владельцу. Требуются диалог, предупреждение и явный checkbox. Очистка передаёт точный список подтверждённых UUID; если корзина изменилась, сервер отвечает 409, интерфейс перечитывает список и требует нового подтверждения. Весь workspace очищается одной транзакцией.
- После операций список, переключатели и счётчик обновляются без перезагрузки. Ответы предыдущего workspace не подставляются в новую корзину.

## Доступ, интеграции и окончательное удаление

`Project` использует Laravel SoftDeletes. Обычные Eloquent-запросы, route binding, ProjectAccess, TaskAccess и REST v1 исключают корзину. Закрыты обычные проектные URL API, экспорт, задачи, обсуждения и скачивание файлов. SPA может загрузить оболочку по прямому URL, но API возвращает 404 и данные проекта не открываются. Текущая проверка клиентской сессии также запрещает проект из корзины; для повторного доступа после завершения сессии может понадобиться исходная клиентская ссылка.

Поиск/переключатели/агрегаты интерфейса используют обычный список проектов. Личные уведомления разрешают проект заново по БД и не доставляются из корзины. Новый транспорт уведомлений или webhook-события удаления не добавлены.

При перемещении ожидающие/обрабатываемые webhook deliveries проекта отменяются. Процессор и ручной retry повторно проверяют наличие обычного проекта; отправка из корзины запрещена. Отменённые доставки автоматически не оживают после восстановления. Уже отправленные события отозвать нельзя; операция ждёт блокировку endpoint, занятую текущей отправкой. История доставки остаётся служебной историей до окончательного удаления.

Повтор REST-запроса с Idempotency-Key проверяет доступность проекта перед возвратом сохранённого ответа. В корзине ответ закрыт (404); после восстановления повтор снова работает. При окончательном удалении сохранённые ответы проекта/его задач заменяются на 410 без содержимого; ключи сохраняются против непреднамеренного повторного создания.

Окончательное удаление удаляет проект, задачи вместе с корзиной задач, комментарии и обсуждения, историю, вложения, секции, настройки, ссылки доступа, прочтения, назначения, integration links, выбранные webhook-связи, события outbox с deliveries/attempts. Общие записи `users`, workspace memberships, другие проекты, токены интеграции и endpoint не удаляются. ID удалённого проекта убирается из `project_ids` приглашений; приглашение без оставшихся проектов отзывается. Редактирование команды другого проекта сохраняет назначения проекта в корзине.

Файлы и thumbnails ставятся в долговечный список `project_file_deletions` в той же транзакции. После commit выполняется физическая очистка. При ошибке хранилища данные проекта уже недоступны, а записи очистки остаются для повторной попытки; восстановление окончательно удалённого проекта через интерфейс невозможно. Фоновая команда повторяет очистку идемпотентно, не требует нового queue worker.

## Production deployment

1. Подготовить проверенный release из зафиксированного чистого checkout штатным `./bin/build-release`. Проверить source commit и SHA-256 в `RELEASE-ARTIFACT.json`. Сборка и push разрешены отдельным запросом; production deployment не выполняется.
2. На staging с production-версией MariaDB/InnoDB проверить новую миграцию и smoke ниже. Перед production сделать согласованную резервную копию БД, private storage и текущих public/private файлов приложения; сохранить `.env`, APP_KEY и секреты. Использовать split layout из `DEPLOY-JINO.md`.
3. Остановить webhook cron/другие фоновые запуски, дождаться текущих отправок и запросов. Включить maintenance, установить согласованные backend/vendor и frontend assets. До возобновления запросов выполнить из private application directory:

```sh
php artisan down
php artisan migrate --force --no-interaction
php artisan optimize:clear
php artisan projects:cleanup-files
php artisan up
```

4. Сохранить существующий cron webhooks. Если уже работает `php artisan schedule:run` каждую минуту, hourly cleanup включён в `routes/console.php`. Иначе добавить отдельный hourly cron с фактическими PHP binary и private path (не дублировать оба варианта):

```cron
17 * * * * umask 077; cd /home/ACCOUNT/private/project-brief-app && /usr/bin/php artisan projects:cleanup-files >> storage/logs/project-cleanup-cron.log 2>&1
```

Успех команды молчит; ошибка возвращает ненулевой exit code и короткое сообщение. Не подавлять stderr или exit status; наблюдать за cron и ротацией лога. После ошибки хранилища проверить повтор команды и отсутствие оставшихся строк `project_file_deletions`.

5. Возобновить фоновые запуски. Smoke на синтетических данных: активный и неактивный проект; правильные счётчики и валюта; корзина → 404 обычного/REST API и скачивания; восстановление исходного состояния и файлов; отказ клиенту и разработчику без права; owner-only purge; foreign workspace 404; очистка только текущего workspace; queue cleanup; мобильные темы. Проверить контрольный соседний проект и его участников. Реальное окончательное удаление проверять только на специально созданном disposable проекте.

## Rollback

Окончательное удаление необратимо в приложении. Возврат таких данных возможен только из согласованной резервной копии БД **и файлов**; отдельно откат кода их не вернёт.

Прежняя версия не знает SoftDeletes проектов и может показать корзину как обычные неактивные проекты. Поэтому нельзя просто заменить код старой версией при непустой корзине, даже оставив новые поля.

1. Остановить фоновые процессы и запись пользователей. До смены кода на текущей версии восстановить все проекты из корзины во **всех workspaces** с сохранением исходной активности либо восстановить согласованную pre-deploy копию БД и private files. Предпочитать восстановление, а не purge ради отката.
2. Запустить `php artisan projects:cleanup-files`; убедиться, что корзина глобально пуста и pending cleanup отсутствует. Текущая `down()` миграции откажет, если остались удалённые проекты или задания удаления файлов.
3. Если новая миграция является последней применённой, ещё на новом коде и в maintenance выполнить `php artisan migrate:rollback --step=1 --force --no-interaction`. Если позже применены другие миграции, подготовить отдельный согласованный план обратного порядка; не откатывать их вслепую.
4. Установить предыдущие согласованные public/private code/assets, очистить caches, вернуть приложение и фоновые процессы. Проверить списки, клиентские ссылки и контрольный проект.

Также допустимо оставить additive schema при откате кода после выполнения пунктов 1–2: ключевое условие — отсутствие проектов в корзине. Новую миграцию нельзя повторно запускать вручную поверх уже существующих полей.
