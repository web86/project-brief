# ProjectBrief 0.6.3 — production deployment и rollback

В релиз входят карточки «Все проекты», команда и корзина проектов. Добавлена миграция `2026_10_26_200540_add_project_trash_lifecycle.php`: `projects.deleted_at`, `status_before_trash`, индекс workspace/deleted_at, таблица `project_file_deletions`. Активность сама по себе не определяет корзину. Новых зависимостей, env-переменных или queue workers нет.

## Обновление

1. Проверьте ZIP SHA-256, `release.json` (version 0.6.3/source commit) и `checksums.txt`. Public/private должны быть из одного архива. Локальная проверка ZIP/SQLite не заменяет staging на production MariaDB/InnoDB.
2. Сохраните согласованную резервную копию БД, private storage, текущих public/private/vendor, `.env`, APP_KEY и остальных секретов. Приостановите запись пользователей, cron webhook и scheduler, дождитесь выполняющихся запросов/доставок. Включите maintenance на установленной версии.
3. Установите `private/project-brief-app` в приватную папку приложения, `public` — в web root по `DEPLOY-JINO.md`. Не публикуйте весь ZIP/private/vendor. Сохраните `.env`, uploads, сессии и настройки; не заменяйте их примерами. Vendor замените целиком согласованным production-комплектом.
4. Сохраняются требования 6.2: PDF создаётся браузером, DOCX — PHPWord. Уберите остатки старых Dompdf, `PdfProjectExporter.php`, `resources/views/exports/specification.blade.php`, `NotoSansSC-Pdf*`, если обновляете наложением. Полные NotoSansSC-Regular/Bold.ttf для DOCX сохраняются. Установите все public/assets JS/Worker/TTF и font-licenses. Старые hashed assets сохраняйте на время активных вкладок либо используйте атомарное переключение версии. HTML/sw.js не кешировать навсегда; CSP должна разрешать same-origin script/worker/font fetch. Node/npm/Composer на production не нужны.
5. Из private application directory выполните до возобновления запросов:

```sh
php artisan down
php artisan migrate --force --no-interaction
php artisan optimize:clear
php artisan projects:cleanup-files
php artisan up
```

Затем выполните принятые на хостинге config/route/view cache команды, если они используются. Не запускайте `first-install` для существующей инсталляции и не повышайте PHP memory_limit ради PDF. Примеры `.env` не меняют реальные параметры.

## Повторная очистка файлов

Файлы/thumbnails ставятся в `project_file_deletions` в транзакции окончательного удаления и удаляются после commit. Если хранилище недоступно, проект уже недоступен пользователям, а записи остаются для повторной попытки. Возврат окончательно удалённого проекта через UI невозможен.

Если `php artisan schedule:run` уже запускается каждую минуту, hourly cleanup зарегистрирован в `routes/console.php`. Иначе добавьте отдельный hourly cron с фактическими путями и PHP binary; не включайте оба варианта одновременно:

```cron
17 * * * * umask 077; cd /home/ACCOUNT/private/project-brief-app && /usr/bin/php artisan projects:cleanup-files >> storage/logs/project-cleanup-cron.log 2>&1
```

Сохраните прежний cron `integrations:webhooks`. Успех cleanup молчит; ошибка возвращает ненулевой exit code и короткое сообщение. Не подавляйте stderr/exit status, настройте наблюдение и ротацию лога. После сбоя storage повторите команду, проверьте отсутствие pending-строк. Возобновите фоновые процессы после smoke.

## Smoke на disposable данных

- Проверьте активный и неактивный проекты, количество клиентов/разработчиков, валюту, прогресс пустого проекта и проекта с удалёнными задачами. Кнопки команды/клиентов должны открывать выбранный UUID.
- Переместите disposable проект в корзину: он пропадает из обычного списка/переключателей; обычный API, прямые задачи, экспорт и файлы недоступны. Клиентские сессии/ссылки не открывают корзину, REST v1 отвечает 404. Проверьте другой workspace и отказ клиенту/разработчику без права.
- Восстановите проект: прежняя активность, задачи, комментарии, настройки, назначения и файлы сохраняются; отдельно удалённые задачи остаются в собственной корзине. Изначально неактивный проект остаётся неактивным.
- Окончательное удаление/очистку проверяйте только владельцем и только на disposable проектах с явным подтверждением. Контрольный соседний и чужой проект, общий аккаунт разработчика и его назначения не повреждаются. Проверьте `projects:cleanup-files` и состояние очереди физической очистки.
- Проверьте RU/EN/TR/ZH-CN, mobile/desktop, light/dark/system, PDF/DOCX, существующие настройки и ссылки клиентов. Уже отправленные webhook нельзя отозвать; pending доставки проекта в корзине отменены и автоматически после восстановления не возобновляются.

## Безопасный rollback

Окончательное удаление необратимо в приложении. Вернуть такие данные можно только согласованным восстановлением БД **и файлов** из backup. Откат кода сам по себе данные не вернёт.

Старая версия 0.6.2 не знает SoftDeletes проектов: простая замена кода при непустой корзине может показать её как неактивные проекты. Даже оставленная additive schema от этого не защищает.

1. Приостановите фоновые процессы и пользовательскую запись. До смены кода восстановите на текущей версии все проекты из корзины во **всех workspaces**, сохранив исходную активность. Альтернатива — согласованный pre-deploy backup БД/storage; он потеряет последующие изменения, это отдельное решение владельца. Не используйте purge просто ради rollback.
2. Завершите `php artisan projects:cleanup-files`. Убедитесь, что `projects.deleted_at IS NOT NULL` и таблица `project_file_deletions` глобально пусты.
3. Если миграция 0.6.3 — последняя применённая, на новом коде в maintenance выполните:

```sh
php artisan migrate:rollback --step=1 --force --no-interaction
```

Обратная миграция откажет при непустой корзине или pending cleanup. При более поздних миграциях согласуйте обратный порядок отдельно, не откатывайте их вслепую. Также допустимо оставить additive schema после выполнения пунктов 1–2.

4. Восстановите согласованный комплект прежних public/private/vendor и `.env`/storage, очистите caches, выполните smoke списков, клиентских ссылок, контрольного проекта и экспорта. Снимите maintenance и возобновите прежние фоновые процессы. Активные вкладки должны перезагрузить приложение.

Production deployment данным релизом автоматически не выполняется.
