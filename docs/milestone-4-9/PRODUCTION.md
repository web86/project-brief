# Milestone 4.9 — обновление production и откат

Полная поставка версии 0.4.9 основана на `web86/projects-manager/main` (`93a1d04`). Включает принятые изменения команды, прав доступа, централизованных уведомлений, корзины и обсуждений. ZIP собирается `./bin/build-release` из чистого коммита ветки `codex/milestone-4-9-comment-attachments`. Push, deployment и GitHub Release выполняются только по отдельному разрешению.

## Перед обновлением

1. Сверить `release.json`, SHA-256 ZIP и `checksums.txt`. Сохранить резервные копии БД, private application/vendor, public index/assets, `.env`, `APP_KEY`, `storage` и release metadata. Время резервирования и последующий ввод данных должны быть известны.
2. Проверить PHP web-SAPI, отдельно от CLI: PHP >= 8.3, GD с JPEG/PNG/WebP, Fileinfo, Zip, `upload_max_filesize >= 20M`, `post_max_size >= 210M`, `max_file_uploads >= 10`, рекомендованная память `memory_limit >= 256M`. 210M и 10 сохраняют возможность прежней загрузки 10 файлов идеи по 20M; сервер дополнительно ограничивает комментарий 5 файлами/40 MiB. Учитывать также лимит HTTP-body и таймаут прокси/веб-сервера. Локальный `api/dev-php/uploads.ini` уже совместим. При меньших фактических лимитах Jino не устанавливать поставку до их согласования; эта задача не меняет серверные настройки.
3. Оригиналы и миниатюры остаются в `storage/app/private/attachments/`; этот каталог должен быть writable для PHP и находиться вне document root. Не создавать публичный storage symlink для него. В архиве нет пользовательских файлов, активных `.env`, базы, паролей, логов или sessions.

## Установка на существующий сервер

Выполнять в действующем private-каталоге приложения, не в document root:

```sh
php artisan down
php artisan optimize:clear
```

Наложить private application и production vendor из ZIP, сохранив действующие `.env`, `APP_KEY` и всё `storage`. Наложить public-файлы в document root. Прежние hashed assets оставить для открытых вкладок и отката. Не переносить private/ или ZIP в document root.

```sh
php bin/check-server
php artisan migrate --force --no-interaction
php artisan optimize
php artisan up
```

Применяется новая миграция `2026_10_25_194153_add_comment_attachments`: `attachments.task_id` становится nullable с сохранением FK; добавляются `attachments.thumbnail_path`, уникальный nullable `comments.submission_key` и `comments.submission_fingerprint`. Старые строки и файлы сохраняются. Новые зависимости и настройки уведомлений не требуются. Нельзя запускать `migrate:fresh`, `db:wipe`, seed, `first-install` или `key:generate` на существующей установке.

## Приёмка

- Клиент: идея → скрепка/выбор файла или вставка скриншота → отправка с текстом и без текста. Разработчик получает одно уведомление, открывает точный комментарий, увеличивает изображение, скачивает оригинал и отвечает документом. Клиент открывает ответ и скачивает документ. Повторить в общей переписке проекта.
- Выбор нескольких файлов, drag/drop, удаление до отправки, 5/20/40 MiB, длинные имена. Ошибка сохраняет форму; повтор после потерянного ответа не создаёт дублей.
- RU/EN, light/dark/system, 320–390 px. Проверить реальное устройство Android Chrome и iOS Safari при наличии.
- Другой проект и отозванный участник не могут скачать файл по UUID. Проверить файлы идеи, комментария идеи и общей переписки отдельно. Неавторизованный запрос не получает файл.
- Перемещение идеи в корзину сохраняет файлы; восстановление возвращает доступ. Прежние комментарии, файлы идеи, unread/deep links, журнал, персональные настройки Email/Push/Telegram, PDF/DOCX продолжают работать. В экспорт не попадают файлы комментариев или их содержимое.

## Откат без потери данных

Предпочтительный откат интерфейса: maintenance → вернуть public/index.html и assets прежней поставки, оставив совместимый backend 4.9 и новую схему → очистить caches → проверить вход и обычные текстовые комментарии → up. Новые комментарии, файлы, миниатюры и ключи повторов сохраняются. Загрузка файлов комментариев исчезает из старого интерфейса.

Полный аварийный откат backend выполняется с сохранением новой additive-схемы и storage. Прежний backend не показывает файлы общей переписки и может показывать файлы комментариев идеи в списке файлов самой идеи: при необходимости полного возврата поведения использовать согласованный snapshot БД и storage, предварительно отдельно сохранив все данные после обновления. Без такого сохранения snapshot приведёт к потере новых комментариев/файлов.

Не запускать `migrate:rollback` после появления новых комментариев 4.9: миграция специально отказывается удалять новые поля, когда есть данные с ключами отправки или миниатюрами. До появления таких данных `down()` может удалить добавленные поля, но оставляет nullable task_id для сохранности общей переписки. Не удалять файлы вручную и не делать task_id NOT NULL при существующих общих вложениях.

Deno Telegram bridge, production credentials и настройки сервера в этой поставке не менялись.
