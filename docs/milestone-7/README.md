## Policy and state

Owners are users with **any active owner membership**, regardless of selected workspace or `users.role`. Developers retain password login and can opt into Passkeys without TOTP. `ProjectClient`, `/access/{token}`, client identities and bearer integration authentication are unchanged.

`guest → pending_2fa → authenticated` is the password flow for owners with confirmed TOTP. Pending login stores a short-lived server challenge without authenticating the Laravel guard. Owners without TOTP log into a restricted `enrollment_required` session: authenticator → confirmed TOTP → save recovery codes → register a UV Passkey. A passkey login proves UV and needs no additional TOTP, but does not exempt the owner from enrolling TOTP and acknowledging recovery codes.

Every web business request passes `EnsureAccountSession`, locale middleware and `EnsureAccountSecurity` **before route model binding and admin authorization**. Restricted owners cannot access profile, workspaces, projects, exports, team, clients or integrations, nor accept an invitation. `/api/session` returns `authenticated:false` with the restricted state. Only status, security setup/confirmation, logout and supported recovery are available. `/admin/security` is outside the admin business shell and resumes after reload. Existing enrolled sessions without a strong authentication stamp must confirm password + factor or UV Passkey. Existing unenrolled sessions must freshly confirm their password before enrolling. Role promotion is checked on the next request.

## Threat model and controls

- Password validation uses Laravel's timeboxed guard validation without logging the user in prematurely; successful validation retains automatic password rehashing. Password theft alone cannot log an enrolled owner in. Email reset also requires a TOTP/recovery code, or a fresh strong session for the same owner; it preserves factors, revokes sessions and never authenticates the reset caller. Legacy owners without factors can reset passwords but remain restricted.
- Fortify generates TOTP secrets/QR/URI and recovery values; Google2FA verifies TOTP. Secrets and codes use Laravel authenticated encryption with APP_KEY. Unconfirmed secrets are stored separately, preserving the old authenticator until replacement confirmation. There is no endpoint to disable mandatory TOTP. The exact accepted time step is committed under a user row lock; all accepted time steps must be newer, across sessions and processes. Window: ±1 thirty-second step. Recovery consumption removes the exact code under the same lock. Codes are not replaced with unknown usable codes.
- WebAuthn creation and assertion use the official package actions. Server options require discoverable credentials and `userVerification:required`. The library verifies origin, RP-ID hash, challenge, signature and counter; the application additionally requires the response user handle to equal the account's opaque HMAC handle. Synced authenticators legitimately using a zero counter remain supported; repeated assertions still fail through one-use challenges. Biometrics never reach this server.
- Registration/confirmation challenges are account-, session-, purpose- and session-version-bound; login challenges are discoverable and session-bound. Public options live in a dedicated DB table for two minutes; password second-factor challenges last five minutes. Deleting the row is atomic; failed WebAuthn attempts consume the challenge. Expired rows are pruned when creating a new challenge. Credential ownership is checked before mutation and confirmation. At most 20 credentials per user.
- User row locks serialize deletion and recovery consumption. The last owner Passkey cannot be deleted. To rotate a Passkey, add and verify a replacement before removing the old one. To rotate TOTP, confirm a new secret before replacing the old secret, and save a new recovery set.
- Security changes, account email/password changes and integration mutations require server-side confirmation within ten minutes. Team and notification destination mutations also require confirmation. Developer confirmation accepts password or UV Passkey; owner confirmation requires password + TOTP/recovery or UV Passkey. HTTP 423 is raised before the mutation; the UI asks for confirmation and only then retries once with refreshed CSRF. Factor changes and email/password changes increment `auth_session_version`, revoke other sessions, and rotate the current session. Existing indefinite bearer integration tokens are intentionally unaffected.
- Fortify and standalone Passkeys default routes are disabled in provider registration. There is no alternate `/login`, `/register`, `/two-factor-challenge`, `/user/passkeys` or standard reset route. Custom routes retain Laravel cookie authentication, request-forgery protection and throttling. Security responses have no-store headers; normal account JSON hides all security fields. Security audits contain only user ID and event names. Credentials, OTPs and operator tokens are excluded from flashed input and never logged by these flows.
- The session stamp is trusted server session state, tied to user ID and `auth_session_version`; no client-supplied assurance values are used. Use database/file/Redis sessions and a shared supported lock store. Cookies are not a supported session driver for route session blocking.

## UX and recovery

`/admin/login` keeps password and adds an explicit Passkey action. Unsupported/insecure browsers explain password fallback. An owner unable to register a Passkey remains in setup with retry, logout and password/recovery options; business privileges are never opened as a fallback. Hardware FIDO2 authenticators are supported. Invitations retain their token only in the page closure while security is completed; reopening the original email link also resumes acceptance.

`/admin/account/security` retains email/password forms and adds device names, creation/last-use dates, rename/remove actions, authenticator rotation and recovery-code display/regeneration. Security text and API messages are supplied in RU/EN/TR/ZH-CN. Existing themes, language switching, accessible native labels and modal handling are reused.

Loss of all factors requires the operator procedure in [PRODUCTION.md](PRODUCTION.md). Email alone does not reset factors. Do not send secrets or QR codes to support.

## Verification

Commands, results and limitations are recorded in [VERIFICATION.md](VERIFICATION.md). Broad business tests use explicitly enrolled owner fixtures and simulated completed authentication; protocol tests use unenrolled owners and real HTTP endpoints with signed software-authenticator payloads. A fixture credential in the broad package regression test is only an enrollment-presence fixture, never evidence of WebAuthn verification. Real WebAuthn is checked separately through the local HTTPS browser and protocol suites.
