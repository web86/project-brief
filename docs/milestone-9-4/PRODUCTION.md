# Project Brief v0.9.4 — обновление и rollback для Jino

Эта инструкция предназначена для отдельно согласованного deployment. Локальная QA не подтверждает поведение Jino/FPM, физического Touch ID или мобильного Safari. Production DB, Jino и внешняя доставка почты в задаче не изменяются. Полная раскладка private/public, PHP 8.4 extensions и cron описаны в DEPLOY-JINO.md.

## Обновление с v0.9.3

1. Проверить SHA-256/CRC production ZIP и сохранить проверенный v0.9.3 ZIP. Подготовить согласованный backup БД, private/public, `.env`, APP_KEY и storage. Сначала проверить обновление на копии.
2. Включить maintenance: `php artisan down`. Заменить private/public runtime v0.9.4, сохранив `.env`, APP_KEY, storage и права. Не использовать migrate:fresh или пересоздание пользователей.
3. Выполнить `php artisan migrate --force --no-interaction`, затем `php artisan optimize:clear` и штатные cache-команды. В v0.9.4 новых миграций нет; при обновлении с v0.9.3 мигратор должен сообщить Nothing to migrate. Если исходная версия старше, следовать также инструкции v0.9.3 для миграции соглашений.
4. Выполнить `php artisan up`, обновить открытые вкладки, чтобы клиент использовал новый bundle. Новых worker/cron/dependency нет. Убедиться, что `storage/framework/cache/data` доступен PHP на запись: стандартные file locks теперь упорядочивают stateful запросы одной сессии, включая фоновые чтения. Это single-host конфигурация Jino; при нескольких runtime hosts lock directory должен быть общим либо следует отдельно настроить общий поддерживаемый lock store. Долгий stateful запрос может задерживать другие запросы той же сессии; проверить exports в обычном smoke.
5. Проверить владельца и назначенного разработчика: профиль, безопасность, уведомления, прямой URL/F5, смену workspace с другим брендом, `/platform` только для действующего platform-admin. Бренд платформы должен оставаться нейтральным. Проверить light/dark/system и футер; приватные реквизиты не должны публиковаться.
6. На тестовой клиентской задаче review проверить «Вернуть в согласованные», затем возврат разработчиком в review и подтверждённое завершение. Отмена не меняет статус; in_progress/done клиент менять не может. При параллельном изменении ожидается 409 и актуальное состояние. Проверить историю, progress и каналы уведомлений с их действующими настройками.
7. На Android Chrome и iOS Safari проверить swipe admin/client/task drawer, вертикальный scroll, ввод в формы, горизонтальные списки, hamburger/backdrop/Escape. Зарезервированные системные жесты должны сохраняться; жест, забранный браузером, не обязан открыть меню. Проверить 390/1440 px, RU/EN/TR/ZH-CN, темы, отступы и длинные названия.
8. Выполнить smoke существующих приглашений, соглашений, SSO origin и двух вкладок Passkey из инструкции v0.9.3. Не создавать реальный доступ и не удалять реальные источники ради проверки. Проверить SMTP, uploads/export и worker/cron по обычной процедуре.

## Rollback на v0.9.3

Включить maintenance. Вернуть проверенные private/public v0.9.3, сохранив `.env`, APP_KEY, storage и текущую БД. Выполнить optimize:clear, штатные cache-команды и up; обновить вкладки. Миграции откатывать не требуется и нельзя: схема не менялась, документы и факты принятия должны сохраняться.

Ранее выполненные клиентом approved/done являются обычными существующими значениями и остаются в БД вместе с историей. Старый runtime не предоставляет новые клиентские кнопки и не отображает новый тип notification event в настройках; при необходимости оценить уже поставленные доставки штатным способом. Не удалять аудит или историю. Соглашения, SSO и Passkey возвращаются к реализации v0.9.3. Старые ограничения персонального брендирования и отсутствие swipe вернутся. Восстановление всей БД из backup — отдельная disaster recovery с учётом новых бизнес-изменений.

## Совместимость ссылок соглашений

Доработка редактора не требует миграций. Для ссылок нужен согласованный новый frontend/backend. Старые опубликованные блоки без href продолжают работать. После обновления проверить вставку/изменение/удаление ссылки, четыре вкладки текста, сохранение и публикацию, публичную страницу и acceptance. Допустимы http/https и mailto без параметров; произвольный HTML не разрешается.

При откате на runtime без поддержки ссылок новые href остаются в JSON БД, а документ отображается обычным текстом. Редактирование и повторную публикацию такого документа следует отложить до возврата совместимого runtime: старый allowlist не принимает href, а старый editor может удалить ссылки при сериализации. Не удалять документы и факты принятия ради rollback.
