# Milestone 4.6 — отчёт

Реализовано в ветке `codex/milestone-4-6-centralized-notifications` от 0.4.5.1
(`2fca739b10078fd4afafdc6ca96473c7f9ce2035`).
Production ZIP собирается из отдельной чистой копии локального коммита.
Инструкция оператора: [PRODUCTION.md](PRODUCTION.md). Описание пакета:
[RELEASE.md](RELEASE.md). Точный commit, размер и SHA-256 — в build-report.json рядом с ZIP.

## Личные настройки

`/admin/settings/notifications` доступен через «Мои настройки → Уведомления»
без выбора проекта или workspace. Предпочтения принадлежат текущему User.
Смена проекта/workspace не меняет адрес, каналы, TelegramConnection или устройства
PushSubscription. Настройки другого администратора недоступны для изменения.

- Email аккаунта используется по умолчанию. Другой адрес получает одноразовое
  подтверждение: 256-битный токен, в БД только SHA-256, срок 30 минут, проверка
  текущего User с блокировкой строки. Повторное/просроченное/чужое подтверждение
  отклоняется. До проверки доставка продолжает использовать прежний адрес.
- Ссылка содержит токен во fragment; интерфейс удаляет его и отправляет защищённый
  POST. Токен не попадает в HTTP URL и referrer. Требуются вход и CSRF; есть лимиты
  попыток и отправки подтверждений. Без SMTP подтверждение не имитируется.
- Push использует существующие подписки: управление и тест текущего устройства,
  остальные устройства сохраняются. Личная приостановка канала не удаляет подписки.
- Telegram использует прежнюю персональную привязку @BriefWeb86Bot, подключение,
  перепривязку, отключение и тест. Переключатель доставки не удаляет привязку.
- Общие тесты и оставшиеся совместимые тестовые API уважают личные запреты;
  Push-тест проверяет принадлежность endpoint текущему пользователю.

API: GET/PATCH `/api/admin/notifications`, POST `/email/verify`, DELETE
`/email/pending`, POST `/test` относительно этого префикса. Доступ требует активного
административного членства, сессии и CSRF для изменений. Клиент не получает доступ.
Персональный API не принимает ID целевого пользователя или произвольные поля.

## Проект и доставка

Проектный экран содержит группы «Действия клиентов» и «Действия команды».
У каждого из девяти событий — активность и адресаты: все подходящие или конкретные.
Настройка подключения и тестирования личных каналов вынесена на общий экран.

Переиспользован ProjectNotificationService, прежние транспорты и ключи дедупликации.
Отправка проверяет событие, выбранных адресатов, актуальный доступ, личное разрешение,
техническую доступность и исключение автора. Для команды используется существующий
ProjectAccess; для клиента — активная идентичность и действующая ссылка текущего
проекта. Сервер отклоняет чужие/отозванные ID и повторяет проверку доступа при доставке.
Пустой список «конкретных» не превращается во «всех». Выбывшие участники показаны
предупреждением и удаляются только из редактируемого списка перед новым сохранением.
Личные предпочтения ProjectClient продолжают работать.

## Миграция и совместимость

Добавочная миграция `2026_10_20_201536_centralize_notification_preferences.php`
добавляет nullable-поля в users и режим/правила в project_notification_settings.
Данные Telegram, Push, история, receipts и ключи дедупликации не удаляются.

Все проекты сохраняют `legacy` до явного подтверждения новых правил. Прежняя
матрица Email/Push/Telegram продолжает ограничивать каналы; событие с полностью
выключенными каналами предлагается выключенным. Переход требует подтверждения
в API и показывает предупреждение об изменении семантики: активное событие
использует каналы, разрешённые самим получателем, включая ранее выключенные только
в проекте. Личные запреты не переопределяются проектом.

Старые проектные email не переписываются и не выбираются автоматически.
Основной владелец видит адреса разных проектов/workspace и выбирает единый:
аккаунт сразу или другой адрес после подтверждения. До выбора legacy-проекты
сохраняют прежний override. После выбора единый адрес действует во всех проектах,
а прежние значения остаются справочно. Старый API не позволяет менять адрес
в обход подтверждения и не позволяет вернуть современный проект в legacy.

## UX

1. Убрана маленькая подпись «Проект» над H1, хлебные крошки сохранены.
2. Стрелка TaskCard осталась только у клиента, вся карточка кликабельна.
3. Название раздела и количество идей сгруппированы с отступом 10 px; длинные
   названия переносятся, сворачивание и управление порядком разделов сохранены.
4. DeveloperTaskPanel больше не показывает раздел ТЗ/«Вверх»/«Вниз». Статус,
   быстрые действия, часы, стоимость, согласование и защита черновиков сохранены.
   Серверные API переноса/сортировки не удалены.
5. «В работе» имеет три точки внутри чипса, цикл 1,8 с и стабильную ширину.
   При reduced motion точки статичны; скринридер читает обычное название.
   «Согласовано» имеет зелёное оформление, отличающееся от зелёного «Готово».
6. Клиентские обсуждения, уведомления и экспорт получили общий компонент:
   «Назад к идеям» по фиксированному маршруту проекта, четыре горизонтальные
   ссылки, aria-current и счётчик непрочитанного. Конфигурация общая с drawer,
   drawer сохранён, административных ссылок нет.

Матрица: администратор/клиент, 1440/1280/768/390/320 px, RU/EN,
light/dark/system, длинные названия, отсутствие горизонтального overflow,

проверяют сохранение черновиков, ошибки сохранения и навигацию задач.
PHP проверяет несколько проектов/администраторов/workspace/клиентов, миграцию
существующих данных, все три канала через подмену провайдеров, персональные
запреты, отзыв доступа, дедупликацию, email proof и безопасность API.

Сборщик дополнительно запускает тесты в чистой копии, ставит production vendor
без dev-пакетов, проверяет платформу, отсутствие секретов и целостность ZIP.
Runtime-тест на временной БД проверяет упакованные миграции, повторную установку,
сохранение APP_KEY, вход/CSRF, личные настройки, подтверждение Email и повторный
токен, клиентский доступ и экспорт. Финальный результат — в build-report.json.

Браузерные сценарии используют API fixtures; автоматические тесты доставки
используют Mail/HTTP/Push fakes. Реальные SMTP, Push и Telegram здесь не проверены:
отдельной среды нет, пользователь согласовал ручную приёмку ZIP. Порядок с двумя
проектами/администраторами/workspace/клиентами приведён в PRODUCTION.md.
