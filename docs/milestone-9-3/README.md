# Milestone 9.3 — Administrators, SSO, Passkey and workspace agreements

База — v0.9.2, commit `9105f2c`, ветка `codex/milestone-9-2-admin-sso-passkey`. Работа выполнена отдельно: `codex/milestone-9-3-admin-agreements`. Push, deployment и изменения production DB не выполняются.

Администраторы и SSO используют существующие карточки, API и модальные компоненты v0.9.2. Сохранены назначения и индивидуальные права проектов, отсутствие обязательных назначений, право создавать проекты, ручные/email-приглашения, ротация и TTL токенов, owner-only управление, аудит и ограничения MFA. Удаление администратора физически удаляет только доступ текущего workspace и назначения; User и другие workspace сохраняются. SSO сохраняет привязку к origin, provenance и прежнюю модель отзыва ключей, handoff и клиентских сессий. Исправлены расстояния между заголовками, подсказками и поиском в длинных секциях модальных окон.

## Соглашение workspace

Настройки владельца: `/admin/settings/agreement`. Переключатель по умолчанию выключен. Четыре языковые вкладки, обязательная дата, простой WYSIWYG (заголовки, абзацы, списки, жирный/курсив), предпросмотр, отдельные сохранение черновика и публикация. Публикация и включение требуют содержательного текста на RU/EN/TR/ZH-CN. Сохранение настроек использует штатный step-up владельца. Новых зависимостей нет.

Источник документа — `workspaces.administrator_agreement`: приватный draft и опубликованный snapshot с UUID и датой редакции. На сервер передаётся только проверяемая структура текста и форматирования. Renderer создаёт только фиксированные элементы, текст выводит через Vue escaping; произвольный HTML, атрибуты, ссылки, SVG, scripts и inline styles не поддерживаются. Вставка в редактор — plain text. Пробелы на границах жирных/курсивных фрагментов сохраняются; исключение TrimStrings ограничено полями структурированного текста. Черновик никогда не попадает в public API, приглашение или client branding.

После принятия приглашения новый WorkspaceMember получает требование, если настройка включена. До принятия сервер блокирует business/admin API текущего workspace, а router выводит отдельную страницу `/admin/agreement` без меню проектов. Login/MFA/security, документ, подтверждение, безопасный выбор доступного workspace, locale и logout остаются доступны. После server-confirmed принятия продолжаются существующие рекомендации по безопасности. Установка MFA или успешный Passkey step-up сами по себе не заменяют принятие.

Подтверждения хранятся в `workspace_agreement_acceptances`: workspace, membership, User, UUID требования и опубликованной редакции, версия-дата, язык и время UTC. Уникальность и блокировки workspace/member делают повторный POST идемпотентным. Устаревшая отображённая редакция получает 409; требуется загрузить и прочитать актуальную. localStorage используется только для обычного выбора языка/темы, не для доказательства принятия. При удалении membership факт принятия остаётся с User/workspace и nullable membership ID.

Обычная публикация исправлений не блокирует ранее работавших администраторов. Явное «Потребовать повторного принятия» требует публикации с более поздней датой и устанавливает новое требование администраторам только этого workspace. Оно проверяется при следующем обращении к защищённому API/входе. Смена языка не создаёт нового требования. Карточки показывают компактное принято/ожидается/повторное принятие; редактирование показывает дату редакции, язык и дату принятия. Загрузка статусов пакетная, без N+1.

## Публичная страница и футер

Постоянный URL `/w/{workspace-uuid}/agreement` доступен без авторизации и показывает только опубликованный snapshot соответствующего workspace, независимо от mandatory toggle. Поддержаны четыре языка (`?lang=ru`, `en`, `tr`, `zh-CN`), печать, mobile и темы. Просмотр ничего не принимает. Документ имеет отдельное имя `administrator_agreement`; принятие не считается согласием клиентов или всех пользователей. Если позднее появятся другие юридические документы, им нужны отдельные источники и статусы, а не переиспользование этих подтверждений.

Один AppFooter встроен в admin/client layouts, авторизацию, приглашение и документ. Он стоит после контента, учитывает sidebar, safe-area и длинное название компании. Использует действующее брендирование; нет копии реквизитов и обязательной подписи Powered by. Ненастроенные юридические/контактные ссылки не выводятся. Контактный email и сайт публикуются только после включения соответствующих флагов в существующем разделе «Брендирование → Футер приложения»; старые приватные contact values автоматически не раскрываются. Банковские данные и адреса не выводятся. Отдельного документа/URL privacy в текущей модели нет, поэтому фиктивная ссылка не добавлена.
