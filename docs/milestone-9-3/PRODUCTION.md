# Project Brief v0.9.3 — обновление и rollback для Jino

Инструкция предназначена для отдельно согласованного deployment. В этой задаче Jino, FPM, production DB, реальные аккаунты и доставка внешней почты не изменялись. Полная файловая раскладка, PHP 8.4 extensions, workers, cron и сохранение private/public описаны в DEPLOY-JINO.md.

## Обновление с v0.9.2

1. Проверить SHA-256/CRC ZIP. Подготовить согласованные backup БД, private/public runtime v0.9.2, `.env`/APP_KEY и private storage. Сохранить старый ZIP. На копии БД проверить DDL и время блокировок; локальный MariaDB test не измеряет нагрузку Jino.
2. Включить `php artisan down`. Установить public/private v0.9.3, сохранив `.env`, APP_KEY, storage и права. Не выполнять migrate:fresh, uninstall или пересоздание пользователей.
3. В private application выполнить `php artisan migrate --force --no-interaction`, затем `php artisan optimize:clear` и штатные cache-команды. Новая миграция — `2026_10_30_090552_add_workspace_administrator_agreements`: nullable JSON workspace, nullable UUID требования membership, одна таблица подтверждений с внешними ключами и уникальностью. Существующие пользователи, права, назначения, Passkey и SSO-токены не переписываются. Не обслуживать business requests новым кодом до миграции.
4. Выполнить `php artisan up`, обновить открытые вкладки. Новая обязательность по умолчанию выключена; существующие администраторы не блокируются. Новых worker/cron/dependency нет.
5. Войти владельцем, проверить TOTP/Passkey, существующие проекты, клиентов и настройки. Проверить отдельные create/edit/invite/delete модальные сценарии, ротацию invitation links, SSO origin/manual grants и отзыв тестовых сессий. Удаление реальных admin/source выполнять только по явному намерению владельца.
6. В «Соглашение администраторов» указать дату и тексты на всех четырёх языках, проверить preview. «Сохранить» оставляет черновик приватным; «Сохранить и опубликовать» обновляет public snapshot. Проверить `/w/{workspace-uuid}/agreement` в отдельном неавторизованном браузере, язык и печать. При включении обязательности новый приглашённый администратор должен принять документ до business API и меню; затем продолжить штатные рекомендации по безопасности. Проверить сохранение языка/даты, повторный вход и logout без принятия.
7. Обычные правки не требуют нового принятия. Для принудительного повторного принятия указать более позднюю дату, выбрать соответствующий флаг и опубликовать. Это осознанно блокирует защищённые запросы администраторов workspace до принятия, включая уже открытые вкладки при следующем обращении. Проверить индикаторы на карточках. Смена языка не должна повторно блокировать.
8. Проверить общий футер владельца, администратора, клиента и приглашения. В «Брендирование → Футер приложения» можно явно опубликовать уже настроенные контактный email/сайт. Они по умолчанию скрыты; банковские реквизиты и адреса не публикуются. Отдельную privacy-ссылку не подменять фиктивной страницей.
9. Проверить RU/EN/TR/ZH-CN, desktop/mobile, light/dark, отступы, focus/scroll/error в длинных окнах. Проверить существующие SMTP, uploads/export, webhook worker и cron.
10. Для platform-admin с действующим доступом проверить две вкладки одной сессии: API-key creation в Integrations и Passkey `/platform`. Вторая подготовка не должна отменять первую; проверить Retry, TTL, browser cancel и разрешённый TOTP fallback. Не логировать credential/challenge bodies или секретные ключи. Физический Touch ID и Jino FPM требуют отдельного live smoke; локальный виртуальный authenticator их не заменяет.

## Rollback на v0.9.2

Предварительно получить решение владельца о временном отключении обязательного соглашения: v0.9.2 не знает нового server gate и публичного документа. При действующей обязательности нельзя молча переключить пользователей на старый runtime. Если владелец не разрешил отключение, держать административный доступ закрытым/maintenance до исправленного runtime.

После согласованного отключения требования включить maintenance, вернуть проверенные private/public v0.9.2 и сохранить `.env`, APP_KEY, storage и additive schema. Выполнить optimize:clear, штатные cache-команды, up; обновить вкладки. Не выполнять migrate:rollback: он удалит документы и факты принятия. Старый код игнорирует новые nullable поля и таблицу. Контактные flags и agreement settings остаются в БД для возврата на v0.9.3.

Публичный URL соглашения и новый футер в старом runtime недоступны. До отката учесть опубликованные внешние ссылки и согласовать временную недоступность документа. Данные подтверждений сохраняются; повторная установка v0.9.3 использует те же требования и принятия. Зафиксировать, какое значение enabled согласовано владельцем.

Физически удалённый доступ администратора application rollback не восстанавливает: при необходимости владелец приглашает существующий User повторно. SSO revocation/provenance/retirement и защита Passkey остаются моделями v0.9.2. Полное восстановление БД из backup — отдельная disaster recovery, учитывающая новые факты принятия и бизнес-данные, не обычный rollback приложения.
