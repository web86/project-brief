# Milestone 4.8.1 — Invitation UX Fixes

База `6ab3389`; отдельная ветка `codex/milestone-4-8-1-invitation-ux`. Push и deployment не выполнялись.

## Что показало исследование

В 4.8 resolve API возвращал только `authenticated: true/false`. Страница не знала Email текущего User и показывала активную кнопку принятия любому авторизованному пользователю. Для другого Email сервер правильно отвечал 403; UI отображал это штатное ограничение красной ошибкой. Кроме того, UI использовал тот же текст для 401, когда существующий аккаунт пытался пройти регистрацию. Без данных конкретной production-сессии нельзя утверждать, какой из этих случаев вызвал исходное сообщение пользователя.

Проверка совпадающего authenticated User не выявила ошибки session cookies/CSRF или запрета корректного принятия. Реальные E2E подтвердили совпадающий аккаунт, выход/вход и назначенные проекты. Найден отдельный воспроизводимый дефект: SQLite сравнивал credentials Email с сохранённым Email с учётом регистра, хотя invitation Email уже нормализован. Существующий User `Legacy@Example.test` без memberships не мог войти как `legacy@example.test`. Теперь поиск credentials выполняется по trim/lowercase и передаёт Auth настоящий сохранённый Email; сравнение при resolve/accept использует общую нормализацию. Это также поддерживает legacy Email с окружающими пробелами. Для production MariaDB с case-insensitive collation данный дефект мог не проявляться.

## Изменения

- Убрана внутренняя пара theme/language; используются прежние контролы App.vue. Уменьшены верхний отступ и расстояния формы, сохранены обычная прокрутка, перенос длинных Email и место под ошибки/уменьшенную высоту при клавиатуре.
- Resolve API возвращает **только Email текущего authenticated User** и вычисленный `accountMatches`. Для гостя оба значения null. Проверка existence чужих аккаунтов, `accountExists` или новый email-lookup endpoint не добавлялись.
- Другой аккаунт заранее видит оба Email и нейтральное объяснение. Основное действие — «Выйти и продолжить». Submit принятия отсутствует; обработчик также блокирует преждевременный запрос.
- После logout сбрасывается CSRF-кэш, очищается прежнее состояние navigation/account, и тот же invitation-token разрешается заново. Токен остаётся в замыкании страницы, не попадает в query, localStorage/sessionStorage, логи или аналитику. Вход и регистрация выполняются на той же странице.
- Для гостя регистрация доступна сразу; существующему пользователю предложен явный выбор входа. Автоматически различать незарегистрированный и существующий Email через публичный ответ нельзя без раскрытия existence, поэтому сервер не выдаёт такой флаг. Если регистрация требует аутентификации, UI нейтрально предлагает вход без заявления о наличии аккаунта.
- После входа UI повторно читает настоящую сессию перед accept. Если аккаунт изменился в другой вкладке и сервер вернул 403, состояние перечитывается и отображается информационное переключение аккаунта.
- Backend по-прежнему проверяет пароль для входа, Email при принятии, одноразовость/expiry, workspace/project memberships и блокировки транзакции. Правила доступа не ослаблялись.

## Проверки

- Laravel: **571/571**, 5725 assertions. Новые тесты проверяют privacy ответа гостю, несовпадающий/совпадающий User, регистр/пробелы, существующего User без memberships, logout/login, назначенные проекты, истечение/отзыв/replay. Прежние auth/session/invitation тесты сохранены.
- Frontend: **212/212**. Новые 8 тестов проверяют реальные переходы invitation flow и запросы: регистрация, вход, отсутствие accept при mismatch, сохранение токена при logout, смена сессии в другой вкладке, спокойный переход ко входу, ошибки ссылок и retry logout.
- E2E: **29 scenarios/configurations** с реальным Laravel API, database sessions, CSRF и локальным SMTP. Включены базовые сценарии 4.8 и новые четыре сценария приёмки; 12 комбинаций RU/EN × light/dark × 320/390/1440 для приглашения. Проверены размеры/переключатели, мобильные tap, прокрутка с viewport height 440, отсутствие токена в query/storage и корректный список проектов.
- Production build, Pint и Prettier. Машинный результат — verification.json; E2E — browser-results.json. Patch дополнительно проверяется после наложения на исходный ZIP 4.8 через packaged-runtime тесты и ZIP checksums.

Скриншоты `entry-*` показывают форму гостя, `switch-*` — другой авторизованный аккаунт. Репрезентативные: `entry-390-en-dark.png`, `switch-390-ru-light.png`, `switch-1440-en-dark.png`. Другие снимки базового E2E подтверждают регрессии 4.8. SMTP Jino и production не затрагивались.

Установка и откат — PRODUCTION.md. Patch не содержит vendor или миграций и предназначен только для базовой версии 4.8.
