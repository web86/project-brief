# Project Brief 0.9.0 — Platform Admin & Usage Monitoring

Ветка: `codex/milestone-9-0-platform-admin`. База: существующий Milestone 8.4. Push, merge и deployment не выполнялись.

`/platform` — отдельная диагностическая панель владельца SaaS. В ней есть обзор, поиск workspace по названию/имени/email владельца, страницы по 25 строк, детали workspace, почасовая статистика API и аудит. Периоды — последние 24/168/720 часовых корзин UTC, включая неполный текущий час. Количества workspace/владельцев/проектов/клиентов/задач — текущий снимок; API, заявки и отправленные уведомления относятся к выбранному периоду. Владельцы включают активные и неактивные owner-membership; глобальное количество владельцев считается по уникальным user ID.

У каждого workspace показаны владельцы, создание и последняя **учтённая** активность, количества, источники интеграций, общее/активное число токенов, webhook-статистика и существующие лимиты API/AI. Клиенты — уникальные нормализованные email внутри workspace из workspace registry и старых project client assignments; клиенты без email считаются по UUID. Проекты и задачи исключают корзину; участники — активные membership. Не выводятся названия и содержимое проектов, переписка, файлы, тела заявок, webhook URL/payload, токены и секреты.

## Авторизация

- Глобальный `users.platform_admin`, default false, скрыт в сериализации модели и отсутствует в mass assignment. Роли workspace и их проверки доступа сохранены.
- Назначение/отзыв — только интерактивная `php artisan platform:admin USER_ID [--revoke]` через доверенный серверный доступ. Для назначения нужны уже подтверждённые TOTP и сохранённые recovery codes. Оператор независимо проверяет личность и вводит точную фразу с ID; `--no-interaction` отклоняется.
- Команда атомарно меняет полномочие, увеличивает session version, отзывает сессии и challenge/proof, пишет аудит. После назначения нужен новый вход.
- Используются существующие password/TOTP/recovery-code/UV-passkey механизмы, password recovery и operator recovery. Новый auth stack не создаётся. Платформенному администратору нельзя выключить обязательный TOTP через интерфейс.
- HTML `/platform` и все GET `/api/platform/*` проверяются backend. Для межтенантных диагностических данных нужен действующий пятиминутный step-up; сам HTML позволяет открыть существующий диалог подтверждения. Лимит платформенных маршрутов — 30/min/user. Существующие CSRF, session version, security headers и login throttles сохранены.
- Назначение не создаёт membership, client session, project access или impersonation. Платформенная учётная запись может работать без членства в workspace.

## Метрики и определения

Глобальный terminable middleware охватывает `/api/v1` и `/api/v1/*`, включая окончательные 401/403/404/405/429/500 и исключения. Он измеряет монотонное время обработки до готового ответа, а после формирования/отправки ответа выполняет один атомарный UPSERT в `api_usage_hours`. Для расширения охвата позже изменяется только условие измерения и добавляется **подтверждённый** контекст соответствующего auth middleware; HTTP-механизм не привязан к внешним токенам.

Ключ: UTC hour + confirmed workspace/source/token ID + allowlisted method + Laravel route template. Неизвестные маршруты схлопываются в `/api/v1/{unmatched}`, нестандартные методы — в OTHER. Token context устанавливается после успешной проверки секрета/срока/отзыва и до workspace throttle. IP throttle до проверки токена и невалидные/истёкшие/отозванные токены остаются в общей категории без workspace. Никакой атрибуции по пользовательским URL/query/body/headers нет.

Суммируются запросы, 2xx, 4xx, 5xx, отдельно 429, суммарные микросекунды и максимум. 429 входит в 4xx; складывать их как независимые категории нельзя. Среднее взвешено по числу запросов, а не усредняется из часовых средних. 3xx входят в общее число запросов. Таблица не хранит отдельные запросы, персональные данные, реальные URL/UUID ресурсов, query strings, тела, IP, email, user-agent, заголовки, Magic Links или bearer tokens. Числовые ID workspace/token/source — технические измерения, необходимые для диагностики.

На MariaDB/mysql используется отдельное короткое соединение с теми же параметрами БД: connection timeout 1 s и `innodb_lock_wait_timeout=1`. Это ограничивает ожидание конфликтующего счётчика и не меняет соединение бизнес-транзакции. Нет retry/read-before-write. Любой сбой телеметрии проглатывается без изменения ответа и без записи секретов/SQL bindings в логи. `PLATFORM_API_METRICS_ENABLED=false` отключает новые измерения; ранее собранные данные остаются видимы. На SQLite в локальных тестах используется основное соединение.

Активность workspace — максимум создания workspace, изменения membership/project и последнего успешного использования токена интеграции. Это диагностическое определение: чтение интерфейса, каждый просмотр клиента и все отдельные изменения задач не являются полным журналом активности. «Активные» означает активность по этому определению в выбранном окне, а не тарифный статус. Отсутствие активности не означает блокировку или удаление.

Webhook-данные читаются из существующих `webhook_events`, `webhook_deliveries`, `webhook_attempts`. Events/delivery cohort считаются по created_at в периоде; статусы delivery — их текущее состояние. Попытки/ошибки/повторные попытки считаются по created_at попытки, включая попытки старых событий. Backlog — все pending/processing независимо от даты. Второй журнал доставок и новый cron не создаются.

`platform_audit` хранит время UTC, actor user ID, action, object type/ID, result. CLI-оператор и гость имеют null actor; CLI-полномочие явно отмечено результатом operator. Входы, изменения безопасности администратора, неуспешный пароль, отказы доступа и просмотры диагностики аудируются. Аудит не содержит email, поисковые запросы и секреты. Через HTTP нет записи/редактирования/удаления аудита. При ошибке обязательного аудита панель не возвращает данные. Это защита на уровне приложения; серверный DBA с доступом к БД остаётся доверенной стороной.

## Тарифы и обслуживание

Тарифы/квоты будущего 9.1 должны принадлежать workspace. В 9.0 нет платежей, новых принудительных квот, подписок, блокировок или изменения прав. Диагностические счётчики допускают потерю и **не могут** быть источником тарификации, финансового учёта или enforcement. Для 9.1 нужны отдельные авторитетные счётчики с транзакционной/idempotent семантикой и проектированием последствий изменения прав/лимитов.

Обязательного cron нет. По решению оператора старую диагностическую статистику можно удалять партиями, например `DELETE FROM api_usage_hours WHERE hour < UTC_TIMESTAMP() - INTERVAL 90 DAY LIMIT 10000`, повторяя до окончания; не применять это к аудиту. По умолчанию история не удаляется автоматически. Следить за объёмом таблиц, connection budget и задержками по процедуре Jino preflight.
