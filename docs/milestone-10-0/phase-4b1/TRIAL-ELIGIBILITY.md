# Durable Trial eligibility and time contract

A verified self-service User may prepare exactly one owner workspace through the existing OwnerProvisioning service. Provisioning runs under User/onboarding locks, creates one active owner membership and references it from onboarding metadata. It grants neither platform_admin, PlanAuthority, imported projects, API credentials, webhooks nor SSO settings.

The existing `owner_trial_claims`, `owner_trial_claim_subjects` and `user_external_identities` remain authoritative. No parallel subscription or role table is introduced. Claim states stay pending or denied in the production implementation. A verified subject already assigned to another durable claim denies eligibility without merging accounts. Deleting/re-registering a User, changing email/provider, unlinking, creating another workspace or transferring ownership does not release the old claim. Subject aliases survive User deletion through the existing durable schema.

Email aliases use existing trimmed/lowercase normalization. Stable provider identity is provider/issuer/subject, never a mutable profile name. Values are HMAC-SHA256 with domain separation and hash version 1; APP_KEY must remain stable. Email/provider additions append aliases, never replace claim dates or reset periods. A conflicting alias records a safe conflict reason, requiring reviewed resolution before future activation. Recovery and password changes do not change Trial dates.

No privacy retention term is invented. `ONBOARDING_SUBJECT_RETENTION_DAYS` must be an approved integer from 1 to 3650. Missing approval leaves `claim_retention_unconfigured`, no eligible verification timestamp and no stored subject aliases for that claim. Configuring a value later does not silently repair existing claims or start a clock. Future reviewed re-evaluation is required. `retained_until` records the configured horizon; there is no automatic alias deletion. Future deletion/anonymization must preserve the approved anti-repeat/privacy contract and be separately reviewed. APP_KEY rotation also requires an explicit identity/alias migration; changing the key breaks deduplication.

`TrialEligibility::proposedTrial` is a pure, non-executable proposal. It requires a verified eligible pending claim and validated immutable published policy with exactly seven Trial days, a nonarchived published paid Studio target and free Basic fallback. It returns concrete version/policy IDs and hashes plus a UTC period proposal. Missing targets fail closed. No automatic seeder/publication is performed.

The future start is completed verification/eligibility time, not form submission, resend, login or optional personalization. Exact end is start + 604800 seconds UTC, preserving microseconds, with no Grace. Delayed MFA or agreement completion cannot retime it. This phase creates no active period or countdown. Phase 4B.2 must explicitly decide how dormant pre-activation pending claims are re-evaluated, so it cannot activate already-expired historical proposals blindly.

`tests/Support/TrialActivationFixture.php` is guarded to console/testing and an isolated QA database and is absent from the ZIP. It models atomic subscription/Trial period/policy/Studio/Basic pinning, mandatory audit and replay under locks. MariaDB workers race the same claim and produce one period. This fixture is evidence for the contract, not an application activation endpoint or scheduled executor.
