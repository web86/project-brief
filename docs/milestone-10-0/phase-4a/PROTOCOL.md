# Shadow allocation, frozen transitions and future execution contract

## Current implementation

ShadowGuard uses a code-owned operation→registry mapping and pinned EntitlementResolver. Decision entries contain key, state (would_allow/would_deny/unknown), reasonCode, currentUsage/occupied/reserved, requested delta and effective typed limit. Envelope carries workspace, operation, revision, UTC asOf/validUntil, provenance and durationMicros; enforced=false, authorization unchanged. Planned storage/run/AI/FormWatch adapters are unavailable, never commercial zero/unlimited. Prospective client identity changes that cannot safely be proved have unknown delta. Enum branding mapping requires field-policy review.

No global entitlement middleware. Core task/client/history and safe-reduction observations have no capacity queries. Feature decisions read the pinned configuration (at most six queries in the fixture); memoization is limited to one real request outside mutation transactions, invalidates on clock boundary and is never a persistent permit. Growth scans only requested capacity keys. Current project/agent scans are bounded; client/invite chunks are 200 with 20,000 safety bounds. Over-bound/incomplete does not become an allow decision. Explicit preview scans are bounded to 250 rows per metadata family and refuse larger snapshots rather than truncating them.

Workspace-first order: existing permission/context resolution → workspace mutex → current auth/member/credential recheck → subscription/period/current resources and invitation union → shadow observation → existing mutation/audit. IntegrationWrites observes before deduped replay and rechecks expired/revoked credentials/scopes/grants/generation first. New token service has its own workspace-first transaction for direct callers. Primary preview obtains authority after workspace, outside catalog HTTP authority wrapper. Immutable catalog reads and current shared metadata reads do not create/modify catalog records; normal business shadow paths do not take exclusive catalog/authority locks.

Do not enter future allocation after holding a user/global lock. Account email edits currently retain the existing account-first writer: current invite union rematches users, fingerprint catches identity drift; a cross-workspace email/ownership barrier is still required before commercial enforcement. Existing Phase 1 internal pin/override uses PlanCommands workspace-first; it is not a new owner selection/apply API.

MariaDB 11.8 can reject a locking read after an older consistent snapshot with error 1020. Guard returns unknown/current_snapshot_refresh_required with no decisions, never the stale count. A fresh transaction under workspace mutex reads current count. Preview HTTP returns 409 after rollback. 1205/1213 are propagated within mutation transactions for the existing bounded whole-transaction retry, not masked after an engine rollback. Never retry only the side effect or emit HTTP inside a retried DB callback.

Frozen capture hashes allowlisted project/member/client/agent/invite/reservation/credential binding/grant/source/webhook-filter/subscription/period/override/inventory/cycle/epoch metadata plus client provenance, pinned state and canonical counts. HMAC hides input contacts; raw rows/emails/private content are not persisted in the preview. Selection hash is canonical. Expiry, target hash/revisions, registry/settings/authority revisions and all resource fingerprints are recomputed on reopen/idempotent replay. Owner cannot be excluded. Multiple owners, missing pinned configuration, current cycle uncertainty and unproven mappings require review.

## Pure future contract (no executor)

ResourceSelections::executionContract returns schemaVersion1, executable=false/preparation_only, workspace/expected revision/resource fingerprint/target hash/selection hash, exact selected client participations, approval prerequisites, deterministic hold/retain proposal receipts, and batches of at most100. Receipt identity binds workspace, subscription revision, target hash, selection hash, resource kind/ID and action. Retain is a proposal, never an automatic rearm. Plans/items/events are the only transition metadata written now; no subscription change, cycle, resource hold or epoch is created.

Future executor must authenticate/authorize and verify all approvals including pinned policy/transition rule and branding allowlist, lock workspace first, catch up UTC boundaries, recheck current selection/fingerprints/expected revision and object ownership, then atomically record change+resource-overlay receipt+audit. Workspace revision and per-resource receipts must be verified before every resumed batch. Unknown result is reconciled by the same receipt, never duplicated by inventing a new key. Partial terminal outcomes: applied/failed/needs_review/compensated; a single failed workspace cannot silently mark the whole rollout applied. Final completion requires all receipts plus mandatory audit.

Compensation may restore only overlays/revisions owned by that transition; it cannot resurrect a user's manual inactive/delete/revoke, resend an agent run, restore an old credential or undo a later authorized transition. Capture baseline overlay revisions; drift requires human review and append-only recovery receipt. Existing data/history, owner security/login and authorized PDF/DOCX/download remain available. This is a required protocol for 4B, not working commercial execution.

## Webhook network boundary

Preparation transaction: workspace (including independent endpoints) → global lease → endpoint/filter/current personal-agent scope → delivery claim, then webhook.send observation. Commit claim/attempt and bounded 90-second availability before DNS/TLS/HTTP. Network transport preserves SSRF checks, TLS, HMAC, response-size limits, 3-second connect/8-second total timeout and happens outside the transaction. Completion repeats workspace → lease → endpoint → delivery, checks lease owner/attempt/status and endpoint enabled/secret version before recording outcome.

Already sent network requests cannot be unsent by concurrent revoke. Endpoint change cancels completion; missing delivery cannot be recreated. A process/DB failure after send leaves a durable processing claim; later retry may redeliver the same delivery UUID. Delivery is at-least-once, so receivers must dedupe by existing X-ProjectBrief-Delivery. No business lock is held for remote transport; test verifies transaction level equals its pre-call test baseline. Commercial execution epochs and precise rearm/cancellation barriers still belong to 4B.
