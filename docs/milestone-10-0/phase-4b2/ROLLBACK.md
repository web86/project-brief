# Rollback и карантин после первой приостановки

Откат одного кода на v0.9.16 с рабочей базой Phase 4B.2 небезопасен после появления suspension cycle или execution epoch. Проверка исходников `ab6af9a` показала, что старые ProjectAccess, bearer middleware, WebhookProcessor и ClientSso принимают решения по базовым статусам, credentials и grants. Эти записи намеренно сохраняются при тарифной приостановке. Старый runtime не применяет исключения held resources и не сверяет epoch receipts перед повторным исполнением.

Это проверка кода, а не репетиция восстановления на Jino.

## Forward fix

1. На уровне входного прокси или hosting maintenance закрыть весь публичный трафик к экземпляру, включая UI, API, SSO и прямой адрес origin. Выключить cron и ручные workers. Дождаться завершения ранее запущенных процессов. Уже отправленные внешние вызовы сверить с получателями по delivery ID.
2. Сделать согласованный снимок базы, файлов и метаданных фоновых заданий. Зафиксировать код, checksums и последний audit revision. Сохранить cycles, resource states, epochs, claims, subscription periods и audit. Секреты, токены и содержимое задач в отчёт не включать.
3. Собрать исправление от последнего runtime с действующими guards. На изолированной копии проверить восстановление, отсутствие доступа к held проектам и отказ по старым webhook deliveries, Agent runs, idempotency keys и SSO handoffs. Проверить сохранность owner-доступа к истории и разрешённому экспорту.
4. Вернуть исправленный runtime с сохранённой базой и файлами. Перед снятием внешнего карантина сверить ревизии и отрицательные тесты. Возобновить только workers исправленного runtime. Rearm выполняется только явным подтверждением и с новой epoch.

Если доступен только старый runtime, экземпляр остаётся в карантине без внешнего трафика и фоновых заданий. Восстановление снимка до приостановки допустимо для изолированной диагностики. Публичный возврат такого снимка требует отдельного решения о потерянных записях и повторном исполнении. Простая смена Observe, удаление marker или сброс очереди не считаются процедурой восстановления.

До canary нужно отрепетировать блокировку прямого origin и cron, восстановление согласованного снимка и forward fix на согласованном стенде.

## Изолированная браузерная проверка архива

`tests/platform-plans.browser.mjs` с `UX_PACKAGE_ROOT` и `UX_REHEARSE_MARIADB=1` использует одноразовую MariaDB 11.8.9 с портом на loopback. После Basic останавливает HTTP origin, проверяет его недоступность, загружает дамп в отдельную БД и сверяет SHA-256 строк suspension cycles и execution epochs. Затем поднимает тот же runtime с восстановленной БД, проверяет доступ к выбранному проекту и запрет превысить Basic capacity, продолжает manual paid, restore и rearm.

До expiry создаются синтетические receipts для Agent, Webhook, External API и SSO. После восстановления и rearm проверяются отказ по API idempotency key, отказ по shared Agent run без выдачи инструкции, отказ по неистёкшему SSO handoff и отказ ручного Webhook retry. Независимый worker проверяется с перехваченным HTTP transport. Cron в сценарии выключен. Запуск без `UX_REHEARSE_MARIADB=1` использует копию SQLite.

Результаты прогона фиксируются в QA.md репозитория. Временные тестовые данные и access receipts не включаются в отчёт и production ZIP.
