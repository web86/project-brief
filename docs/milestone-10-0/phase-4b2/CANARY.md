# Commercial canary — условия допуска

Статус — запуск закрыт. Production registration и Trial выключены. Ниже порядок проверок для будущего оператора после завершения реализации. Утверждение и действия в production выполняются отдельным поручением.

1. На копии production с изолированными почтой и интеграциями проверить полный цикл Verified → Trial → Basic → выбор ресурсов → manual paid → выборочное восстановление. Прогнать PHP 8.4/MariaDB, race tests, проверки extracted ZIP и имитацию остановленного cron.
2. Сверить UUID и hashes опубликованных версий Studio, Basic и policy. Сверить Trial и Grace по 604800 секунд, Basic limits и legacy cohort. Незавершённый accounting review блокирует допуск. Публикация проходит отдельно от миграций.
3. Подтвердить вход, доставку email verification и уведомлений на согласованные тестовые адреса. При использовании OAuth проверить только отдельно настроенные провайдеры. Утвердить сроки хранения claim hashes, процедуру ротации ключа и правила для dormant claims.
4. Отрепетировать остановку новой активации, восстановление из резервной копии и продолжение обслуживания существующих периодов. Проверить, что emergency режим сохраняет действующие execution barriers и исключает запуск старых jobs.
5. После отдельного разрешения ограничить первую выборку новыми подтверждёнными владельцами. Primary PlanAuthority с fresh MFA подтверждает allowlist подготовленных claims. Сервер проверяет актуальную ревизию и закрепляет опубликованные версии.
6. Сверять агрегаты claims, фаз, cycles, epoch denials, уведомлений и ошибок перехода. Остановить при расхождении UTC boundary, повторном Trial, доступе к held ресурсам, утечке tenant данных, отправке старого job или изменении Compatibility. Действующие циклы и audit сохраняются для reconciliation.

## Контроль восстановления

До первого canary на изолированной копии сохранить receipts до expiry и проверить их после rearm. Старый bearer key с прежним idempotency key, shared Agent key со старым run ID, неистёкший старый SSO handoff и старая независимая Webhook delivery должны получить отказ или отмену без внешней отправки. Новый запрос должен работать только в выбранных проектах, с действующими клиентскими участиями, grants и credentials. Проверить, что отозванные credentials и просроченные приглашения не ожили.

Перед допуском зафиксировать commit и checksums проверенного production ZIP, текущие revisions опубликованных тарифов и policy, итоги MariaDB race tests и тестовой доставки. Отдельно записать результат репетиции закрытия прямого origin и остановки cron по [процедуре карантина](ROLLBACK.md). После появления первого cycle откат одного кода на старый runtime закрыт.

На Jino действия выполняются только после согласования окна обслуживания из основного runbook Jino.

## Подготовка первого владельца

1. Оставить `REGISTRATION_ENABLED=false` и `TRIAL_ACTIVATION_ENABLED=false`. Проверить SMTP и утверждённый `ONBOARDING_SUBJECT_RETENTION_DAYS`.
2. Primary PlanAuthority проходит fresh MFA. Из этой же сессии отправляет `POST /api/platform/registration-canary/invite` с CSRF, новым `Idempotency-Key` и телом `{"email":"test-owner@example.com"}`. Ответ HTTP 201 содержит `data.url` и `data.expiresAt`. Передать URL владельцу приватно. Срок 30 минут. Повтор с тем же ключом не возвращает секрет. Если URL утрачен, дождаться истечения и выпустить новый с новым ключом.
3. Владелец открывает `/register#invite=…` в гостевой сессии и вводит выданный email. Ссылка расходуется при создании аккаунта. Для регистрации по canary invite доступен только email и пароль. OAuth создаёт аккаунт через отдельный callback и не погашает email-bound приглашение атомарно, поэтому Google, Яндекс ID и GitHub здесь скрыты. Обычная публичная форма показывает настроенных провайдеров только при открытых registration gates. Затем владелец подтверждает email обычным письмом, подтверждает TOTP, сохраняет recovery codes и принимает требуемое соглашение.
4. После email verification появляется pending claim. Для приватной операторской сверки можно прочитать `owner_trial_claims.uuid` по ID этого подтверждённого пользователя, сверить `state = 'pending'` и `period_id IS NULL`. Допуск к Trial выполняется отдельно по процедуре ниже. Выдача и погашение ссылки записываются в audit. Ссылка, токен и email в audit не включаются.

## Серверные действия оператора

1. Оставить `REGISTRATION_ENABLED=false`. Канал допуска принимает только UUID уже подготовленных verified owner claims с завершённой настройкой безопасности и соглашениями. Лимит — десять конкретных claims на 24 часа. Проверить наличие подготовленных claims в согласованном контуре до начала окна.
2. В сессии primary PlanAuthority пройти fresh MFA. Для каждого POST на `/api/platform/registration-canary/{action}` передать стандартный CSRF-заголовок, `If-Match: "revision:N"` с актуальной ревизией настроек и уникальный `Idempotency-Key`. При повторе того же запроса использовать исходный ключ и тело. На конфликте ревизии перечитать состояние и заново подтвердить действие.
3. Вызвать `approve` с `claims` и объектом `evidence`. Передать реальные SHA-256 документов или логов по пяти ключам `lifecycle`, `execution_barriers`, `rollback`, `notification_delivery`, `trial_claim_policy`. Хэши фиксируют операторское подтверждение. Сервер отдельно проверяет опубликованные контракты, legacy cohort, незавершённый accounting review, конфигурацию почты и retention.
4. Только после отдельного разрешения для canary включить `TRIAL_ACTIVATION_ENABLED=true` в согласованном контуре. Вызвать `admit` с `{"claimId":"<uuid>"}` и ревизией из ответа `approve`. Для каждого владельца требуется отдельное действие. Сервер повторно проверяет permit, allowlist, текущие версии и срок. Срок Trial отсчитывается от verified timestamp.
5. Для остановки вызвать `stop` с `{}` и текущей ревизией. Затем вернуть `TRIAL_ACTIVATION_ENABLED=false` и перестроить config cache. Остановка разрешения сохраняет уже созданные Trial, периоды, ограничения, cycles и epochs. Действия approve, admit и stop фиксируются в `plan_events`.

Для read-only сверки ревизии запросить `SELECT revision FROM plan_settings WHERE id = 1` в согласованной БД. Проверить последние действия по `plan_events.action IN ('canary.approve', 'canary.admit', 'canary.stop')` и их `before_revision` / `after_revision`. UUID claims сверять по утверждённому списку отдельно от отчётов QA.
