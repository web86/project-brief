# Commercial canary — условия допуска

Статус — запуск закрыт. Production registration и Trial выключены. Ниже порядок проверок для будущего оператора после завершения реализации. Утверждение и действия в production выполняются отдельным поручением.

1. На копии production с изолированными почтой и интеграциями проверить полный цикл Verified → Trial → Basic → выбор ресурсов → manual paid → выборочное восстановление. Прогнать PHP 8.4/MariaDB, race tests, проверки extracted ZIP и имитацию остановленного cron.
2. Сверить UUID и hashes опубликованных версий Studio, Basic и policy. Сверить Trial и Grace по 604800 секунд, Basic limits и legacy cohort. Незавершённый accounting review блокирует допуск. Публикация проходит отдельно от миграций.
3. Подтвердить вход, доставку email verification и уведомлений на согласованные тестовые адреса. При использовании OAuth проверить только отдельно настроенные провайдеры. Утвердить сроки хранения claim hashes, процедуру ротации ключа и правила для dormant claims.
4. Отрепетировать остановку новой активации, восстановление из резервной копии и продолжение обслуживания существующих периодов. Проверить, что emergency режим сохраняет действующие execution barriers и исключает запуск старых jobs.
5. После отдельного разрешения ограничить первую выборку новыми подтверждёнными владельцами. Primary PlanAuthority с fresh MFA подтверждает конкретные версии, размер выборки и критерии остановки. Нужен реализованный revision-bound серверный gate. Текущая ветка его ещё не содержит.
6. Сверять агрегаты claims, фаз, cycles, epoch denials, уведомлений и ошибок перехода. Остановить при расхождении UTC boundary, повторном Trial, доступе к held ресурсам, утечке tenant данных, отправке старого job или изменении Compatibility. Действующие циклы и audit сохраняются для reconciliation.

## Контроль восстановления

До первого canary на изолированной копии сохранить receipts до expiry и проверить их после rearm. Старый bearer key с прежним idempotency key, shared Agent key со старым run ID, неистёкший старый SSO handoff и старая независимая Webhook delivery должны получить отказ или отмену без внешней отправки. Новый запрос должен работать только в выбранных проектах, с действующими клиентскими участиями, grants и credentials. Проверить, что отозванные credentials и просроченные приглашения не ожили.

Перед допуском зафиксировать commit и checksums проверенного production ZIP, текущие revisions опубликованных тарифов и policy, итоги MariaDB race tests и тестовой доставки. Отдельно записать результат репетиции закрытия прямого origin и остановки cron по [процедуре карантина](ROLLBACK.md). После появления первого cycle откат одного кода на старый runtime закрыт.

Операторская проверка в этой ветке остаётся закрытой до подтверждения этих условий. На Jino действия выполняются только после согласования [окна обслуживания](JINO.md).
