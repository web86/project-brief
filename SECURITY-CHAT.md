## Приватный чат команды

По уточнению владельца проекта старые общие сообщения разработки заменяются внутренним каналом. Миграция помечает `comments.task_id IS NULL` как `team_only=true`, включая их файлы; сообщения задач и идей не меняются. Существующие таблицы сообщений, файлов и прочтений переиспользуются.

`TeamChat::authorize` разрешает доступ только активному владельцу текущего workspace либо активному администратору с явным назначением в конкретный активный проект. Отдельное право суперадминистратора для обычного чтения/отправки чата не требуется. Клиент, чужой workspace, посторонний или отозванный участник доступа не получает. Списание назначения не удаляет учётную запись.

Малый API `/api/admin/projects/{project}/team-chat` проверяет контекст при списке, отдельном сообщении, POST, read и скачивании. При записи назначение перепроверяется с блокировкой внутри транзакции. Файл ищется одновременно по UUID и принадлежности приватному сообщению этого проекта. Знания UUID недостаточно. Ответы no-store; inline только для разрешённых растровых изображений, CSP sandbox и nosniff. Общие endpoints файлов не возвращают приватные вложения.

Глобальные scopes `Comment.public_channel` и `Attachment.public_channel` исключают приватные сообщения и файлы из существующих клиентских и интеграционных Eloquent-выборок. Scope явно снимается в авторизованном TeamChat/его дедупликации, служебном окончательном удалении, счётчиках текущей команды и обработчике приватных уведомлений. Счётчики возвращают только количество, а приватные внешние уведомления — только метаданные, без текста. Сырые SQL-выборки LiveNotifications отдельно фильтруют `team_only` для клиентов. Клиентские счётчики не считают приватные сообщения. Экспорты PDF/DOCX используют задачи и их публичные комментарии, а не приватный канал. Комментарии задач не изменены.

Старые endpoints общих обсуждений сохраняются для совместимости, работают только с публичным каналом и не раскрывают team-only данные. В UI у команды вместо прежней вкладки открыт приватный чат, у клиента остаётся обсуждение задач.

## Уведомления и интеграции

Обычные комментарии задач/публичные комментарии могут передаваться разрешённым адресатам email, push и Telegram через NotificationPayload, ProjectNotificationService и настройки проекта. WebhookEvents публикует подписанные события клиентских комментариев по существующим scopes/filter. REST integrations с нужным scope могут читать публичные комментарии и разрешённые файлы. Это серверная обработка текста, не E2EE.

Для `team.message_created` получатели — только `ProjectAccess::recipients`: текущий владелец и явно назначенные активные участники. Учитываются правила событий/получателей и персональные каналы, автор исключается. Email идёт на персональный адрес участника, а не legacy override проекта. Приватные уведомления содержат только факт нового сообщения, название проекта и авторизованный deep link; без текста, выдержек и вложений. Клиентам события не доставляются. `CommentSubmission` не вызывает клиентский WebhookEvents для приватного сообщения.

Live Sync переиспользует существующий coordinator, курсоры, backoff, видимость и межвкладочную координацию. Новый таймер/очередь/Redis/WebSocket не добавлен. События сообщений, файлов и read чата имеют kind `team`; клиентская выборка исключает этот kind. Admin live notification preview пустой. Непрочитанное хранится на сервере в существующих comment_reads; собственные сообщения не увеличивают unread. Содержимое чата не записывается в localStorage/BroadcastChannel.

POST требует submissionId. Project row lock и сохранённый hash ключа пользователя/проекта/канала/попытки обеспечивают однократную запись при повторе; fingerprint запрещает использовать тот же ключ с другим содержимым (409). Вложения и DB-запись обрабатываются атомарно существующим AttachmentStorage. Текст выводится Vue interpolation, без v-html. Формы и выбор workspace сбрасывают приватное состояние при смене личности; API остаётся источником авторизации.

## Логи и доступ к исходному тексту

SafeExceptionReporter (`api/bootstrap/app.php`) заменяет обычное логирование исключений метаданными: diagnostic ID, класс, имя файла, строка. SQL bindings, сообщение исключения, URL и аргументы стека не логируются этим механизмом. NotificationService логирует только event/channel/error code/type. Новый чат не добавляет логирование текста, заголовков, файлов, токенов или WebAuthn.

Администратор сервера, DB/backup-оператор с соответствующими правами и PHP-приложение способны прочитать исходный текст и файлы. Workspace owner и назначенная команда читают приватный чат через API. Platform diagnostics не получают нового доступа к содержимому. Внешние системы логирования, APM, веб-сервер, SMTP/Telegram-провайдеры и конфигурация хостинга требуют отдельной проверки на месте; локальный аудит не доказывает отсутствие содержимого в произвольно настроенном внешнем proxy/APM.

## Возможное отдельное улучшение шифрования при хранении

После отдельного согласования: версия ciphertext + per-workspace data key, AEAD/envelope encryption, ключи отдельно от DB, ограниченные сервисные права; отдельная обработка вложений и постепенный backfill с журналом прогресса. Оценить перед реализацией:

- Поиск: SQL LIKE по ciphertext невозможен; потребуется ограниченный серверный поиск после расшифровки либо согласованный индекс с явными утечками метаданных.
- Экспорт/уведомления: расшифровка только после текущих permission checks; исключение plaintext из промежуточных файлов, очередей и логов.
- Backup: согласованная резервная копия ciphertext и защищённое отдельное хранение ключей; потеря ключа означает потерю данных.
- Ротация: key ID, период совместимости, повторное оборачивание data keys и тест восстановления; не заменять APP_KEY без анализа остальных Laravel secrets.
- Нагрузка Jino: замеры CPU/I/O, chunked attachments, память и время миграции; поиск/массовый экспорт будут дороже.

Это будет серверное шифрование при хранении, а не E2EE: приложение всё ещё должно расшифровывать разрешённые операции. В v0.9.5 такая миграция не выполняется.
