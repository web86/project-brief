Connect an external client area

Trusted sign-in lets a signed-in customer open their existing Project Brief projects from your website. It requires server-side integration. Keep the API key on your server.

  1. In Settings → Integrations → SSO, add a source for the external client area.
  2. Set its exact HTTPS origin, for example https://portal.example.com. Do not include a path, query, fragment or credentials.
  3. Create an API key with clients:sso permission for that source. Copy the secret when it is displayed, then store it in your server's private configuration.
  4. Implement the server-to-server handoff below. Your server must verify its customer session and the customer's confirmed email.
  5. Enable SSO and choose available projects. Projects created or approved through this source connect automatically. Add an existing project manually when its customer needs to open it from this client area.
  6. Test with an active customer who already belongs to an active allowed project. Then check source/key revocation and the email sign-in fallback.

Server API

Send an authenticated server-to-server request to your Project Brief origin:

POST /api/v1/client-sso/handoffs
Authorization: Bearer YOUR_SERVER_API_KEY
Content-Type: application/json

{
  "projectId": "SAVED_PROJECT_UUID",
  "externalUserId": "STABLE_CUSTOMER_ID",
  "email": "customer@example.com",
  "emailVerified": true
}

Use the project UUID saved in your own trusted order or account records. Do not accept the project, email or external customer ID directly from browser input. The API does not create customers or projects.

A successful response includes data.code, data.postUrl and data.expiresAt. The code is single use and expires after 60 seconds. Send it immediately from the external client area using an HTTPS form POST to the fixed /client-sso/enter URL on your Project Brief origin. Use a hidden form field named code. Set Referrer-Policy: origin on the transfer page; the browser must send the exact configured Origin.

Never put the API key or handoff code in URLs, browser storage, analytics or request-body logs. Verify TLS certificates. Do not accept an arbitrary transfer URL from customer input. Provide a normal form submit button if JavaScript is disabled.

Identity, project access and revocation

The first handoff binds the source, stable external customer ID and normalized email. Changing identity requires resolving the conflict on the server; the integration never silently rebinds a customer. Workspace administrators and owners cannot use client SSO to obtain staff access.

Keep provisioning and SSO credentials attached to the same persistent source when automatic project access is needed. Rotate credentials by issuing a new key for the same source and revoking the old one. Each source can have separate keys and its own manually allowed projects.

Disabling or changing source settings revokes its SSO handoffs and sessions. Revoked or expired keys, removed project permission, inactive customers/projects and a changed email deny access. Existing sessions for a different identity are preserved. The ordinary email sign-in link remains available.

Errors

401: invalid, expired or revoked key. 403: scope, source, project or customer access denied. 404: project unavailable in this workspace. 409: identity binding conflict. 413/415/422: invalid request. 429: wait before retrying.

Implement the flow in trusted server code and test the complete journey across both HTTPS sites. Keep a normal email sign-in option available to customers.
