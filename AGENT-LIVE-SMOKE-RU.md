# Короткая проверка AI-агентов после установки v0.9.10

Эта инструкция для владельца Project Brief. Выполняйте её самостоятельно после
отдельно согласованной установки релиза. Возьмите отдельный тестовый проект,
вымышленные задачи и файлы без секретов и данных клиентов.

**Важно:** создание ключа и регистрация агента не запускают LLM. Для ответов нужен
внешний исполнитель на отдельной машине или у вашего поставщика. На Jino ничего
дополнительно устанавливать не нужно. Общий ключ даёт его обладателю возможность
представляться любым связанным агентом. Для независимых поставщиков выдавайте
отдельные ключи, даже если у них одинаковые scopes.

1. В «Интеграции → API-ключи» нажмите «+ Создать API». Выберите тип «AI-агенты»,
   название «Проверка агентов» и короткий срок действия. Отметьте профиль, чтение
   назначенных задач, отчёты, чтение запусков/контекста, подтверждение начала,
   чтение/ответ в приватном чате. Для файлов добавьте чтение вложений и загрузку
   результатов. Подтвердите действие существующей MFA.
   **Ожидается:** ключ создаётся даже без зарегистрированных агентов. Секрет виден
   один раз. Сохраните его в защищённом месте; не отправляйте в чат или отчёт.

2. Во вкладке агентов создайте «Тестовый аналитик» и «Тестовый рецензент». У обоих
   выберите этот же API-ключ и тестовый проект. В инструкции напишите, например:
   «Анализируй требования; отчёт на русском; не придумывай ответы за клиента».
   Права API определяются scopes выбранного ключа; отдельного набора прав в форме нет.
   **Ожидается:** у обоих один ключ; старый секрет повторно не раскрывается. Если
   ключа нет, агента можно сохранить без него. Создайте ключ отдельно в разделе API,
   затем выберите его в настройках агента; без ключа API недоступен.

3. Откройте «Команда» тестового проекта и его карточку в списке проектов.
   **Ожидается:** оба агента добавлены автоматически; счётчик с роботом показывает
   двух фактических участников. Одни owner grants без membership не учитываются.

4. В настройках проекта заполните инструкции для AI, например:
   «Стек Vue/PHP. Проверяй доступность клавиатурой. Не включай секреты».
   **Ожидается:** настройки сохраняются после нужного подтверждения доступа.

5. Создайте несогласованную синтетическую задачу. Разработчик может открыть её
   редактирование и изменить описание до согласования клиентом. В правой колонке
   под «Управление задачей» назначьте аналитика.
   **Ожидается:** появляется чат с его именем. Назначение из новой карточки ещё
   не запускает пустой запрос к модели.

6. Напишите первое поручение в чате: «Найди два спорных требования и предложи
   критерии приёмки формы обратной связи». Можно выбрать небольшой тестовый TXT.
   **Ожидается:** сообщение сохранено; состояние честно показывает ожидание.
   Разрешение прикрепить файл не выдаёт агенту право читать его.

7. На **внешней машине**, где уже есть Node.js 22+, возьмите
   `agent-api/examples/collaboration.mjs` из ZIP. Подготовьте локальный env вне
   репозитория с PROJECT_BRIEF_URL (ваш HTTPS-адрес), PROJECT_BRIEF_TOKEN (секрет
   общего ключа), PROJECT_BRIEF_AGENT_ID (UUID из строки «ID агента (API)» на карточке аналитика).
   Для модели добавьте AGENT_PROVIDER=groq, GROQ_API_KEY и GROQ_MODEL.
   Ключ Groq хранится только у внешнего исполнителя. Для первого теста можно
   оставить AGENT_PROVIDER=deterministic — это проверит цепочку без AI-запроса.
   Для разрешённых небольших TXT-файлов отдельно включите AGENT_READ_TEXT_FILES=1.
   Остальные форматы требуют внешнего исполнителя, умеющего с ними работать.
   **Ожидается:** программа отправляет X-ProjectBrief-Agent-ID вместе с Bearer;
   один общий Bearer без явного связанного ID не проходит авторизацию.

8. Загрузите переменные в окружение своего терминала и выполните
   `node collaboration.mjs`. Не печатайте секреты командами диагностики.
   **Ожидается:** программа получает разрешённый контекст, подтверждает начало и
   возвращает приватный ответ в тот же чат. В Project Brief нет статуса «Онлайн»;
   успешная доставка webhook ещё не означает, что модель начала работу.

9. Измените инструкции регистрации или проекта и отправьте уточнение в чат.
   Запустите внешний пример ещё раз либо дождитесь вашего webhook-исполнителя.
   **Ожидается:** появляется второй ответ; первый остаётся в переписке. Новые
   инструкции используются только следующим запуском, старые условия не меняются.
   Длинный ответ раскрывается кнопкой «Развернуть» без нового окна.

10. Проверьте прикреплённый тестовый файл у разработчика и в клиентском доступе.
    **Ожидается:** разработчик может скачать файл; клиент не видит приватную
    переписку и файл. Агент скачивает файл только при подходящем scope
    и текущем назначении. У другого агента этот файл недоступен.

11. Нажмите «Поделиться с командой» или «Поделиться с клиентом» под ответом.
    Введите только проверенное резюме; явно выберите нужные ссылки и файлы.
    **Ожидается:** появляется отдельная копия в выбранном канале. Исходный ответ
    остаётся приватным. Снятие назначения оставляет чат только для чтения.

12. Если у внешнего исполнителя готов собственный HTTPS-получатель на порту 443,
    откройте «Интеграции → Webhooks → + Создать webhook». Выберите тип событий
    «Агенты», укажите название, HTTPS-адрес, нужные события и проекты. Получатель
    независим от регистрации: его можно создать до первого агента. Один webhook
    принимает события аналитика и рецензента; источник указан в payload `agentId`. Передайте
    отдельный одноразовый signing secret только программе-получателю; это не
    API Bearer и не даёт права выполнять операции агента. Получатель должен проверять HMAC исходного тела и timestamp и не
    обрабатывать один event/delivery ID повторно. После создания нажмите тест
    доставки; затем отправьте ещё одно синтетическое поручение.
    **Ожидается:** после очередного штатного cron виден успешный HTTP-статус в
    истории доставок. При временном 503 выполняется retry. Отзыв доступа отменяет
    ожидающие доставки. Не отключайте TLS или SSRF ради неподходящего URL.
    Без работающего внешнего получателя используйте REST-пример из шага 8.

13. Отзовите общий ключ в «API-ключах» и повторите обращение от обоих агентов.
    **Ожидается:** оба получают отказ; ключ исчезает из активного списка и
    селекторов. Отчёты, переписка и аудит сохраняются. Отвязка только одного
    агента, напротив, не отключает другого. Удаление агента из регистрации также
    сохраняет историю для команды и не открывает её новому назначению.

После проверки удалите тестовые доступы и остановите временного внешнего
исполнителя/получателя. Не используйте для smoke реальные клиентские данные.
